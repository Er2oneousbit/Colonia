# Architecture

How Colonia is put together, for whoever touches the code next.

## Big picture

```
            +------------------------- browser only --------------------------+
            |                                                                 |
 index.html |  main.js -> App (app.js) ---- Renderer (render/*)  canvas       |
 or dist/   |               |  \-------- UI (ui/*)            DOM widgets    |
            |               |  \-------- Input (input/*)      mouse/touch/keys|
            |               |  \-------- Sfx, Music (audio/*) WebAudio       |
            +---------------|-------------------------------------------------+
                            v
            +-------------- runs anywhere (browser AND Node) ----------------+
            |  Game (core/game.js)                                           |
            |    map (world/map.js)      typed-array tile layers             |
            |    buildings: Map<id, Building>   walkers: Map<id, Walker>     |
            |    units: Map<id, Unit> (soldiers + raiders), projectiles      |
            |    city: plain object (money, ratings, trade, gods...)         |
            |    systems: sim/*.js       pure functions of (game, ...)       |
            |    events: EventBus  ---> UI/audio/renderer subscribe          |
            +-----------------------------------------------------------------+
```

The simulation never touches the DOM. That single rule is what makes the headless tests (`tests/sim.test.mjs`), the balance simulator (`scripts/simulate.mjs`) and the live main-menu background all work.

## The main loop (`app.js`)

Each animation frame:

1. Add `dt * TICKS_PER_SECOND * speed` to an accumulator and run whole simulation ticks (capped at `MAX_TICKS_PER_FRAME` so a slow frame cannot snowball). An auto-pause stops the loop after the tick that asked for it (below).
2. Keyboard and edge scrolling. Edge scrolling waits for a real pointer move on the current map (`input.mouse.game`): a menu or modal that vanishes under a still cursor only sends `pointerenter`, and its position must not read as "at the screen edge".
3. Render. The leftover fraction of a tick (`alpha`) interpolates walker positions so they glide at 60 FPS even though the sim runs at 12 Hz at 1x. `TICKS_PER_SECOND` only sets the real-time pace: all balance is per tick and per day. Walkers and soldiers count the tiles they walk (`walked`, modulo `STRIDE_WRAP`), and the art swings their legs from that, so steps match ground speed at every game speed and freeze when paused.
4. Refresh UI widgets (HUD 4x/second, info panel ~1.4x/second, advisors every 1.5 s, the Empire map every frame while it is open).
5. Feed the frame's times to the performance readout (`render/perf.js PerfMeter`: the interval since the last frame and each stage's milliseconds) and to the WebGL back end's render scale (`tune()`, see "Composition, render scale and the performance readout").

**Auto-pause** (`ui/autoPause.js`, *Settings*): six switches (a fire, a scouted raid or Caesar's legions setting out, raiders or legions arriving, Caesar's request or call for troops, a collapse, an outbreak of disease; only the arrival on by default), stored in `settings.autoPause` and read through `autoPauseSwitches()` so a switch missing from older stored settings takes its default. The sim labels the messages of those events with a `kind` (`core/game.js message()`: `fire`, `scouted`, `legionMarch`, `raid`, `legion`, `request`, `troops`, `collapse`, `disease`); nothing in the sim reads it, so `npm run sim` is unchanged by it. A fire spreading from one already burning is cause `spread` in `igniteBuilding()` (it reads and burns as `fire`, unlabelled). `App.onGameMessage()` pauses when `autoPauseFor(m, settings)` names a switch, only while `app.ticking` (inside step 1): a console command, a test fast-forwarding with `runDays()` and the menu's demo city (never subscribed) do not pause. The loop's guard is `this.game && this.paused`: the menu's demo city ticks whatever `paused` the last game left. The sticky toast it pushes (`Messages.push` with `sticky`, level `pause`; newer toasts trim the oldest that is not sticky) carries the message's place, `empire` or an `open` function (the Imperial advisor for Caesar's letters, the empire map for the legions setting out) for `openMessage()`, and the frame drops it once the game runs again.

**Building to building** (`ui/cycle.js`): `stepOfKind()` (the panel's arrows and `,` / `.`, the panel's *Next idle*) and `stepIdle()` (the `I` key, through `nextIdleFrom()`, and the Production advisor's button, shown only while something is idle), by id within a kind and by `BUILDINGS` order across kinds, wrapping. Idle is `buildingStatus()` red, or amber unless it is only understaffed (the status carries `understaffed: true`). The panel asks the app (`App.buildingPlace()`) for its place among its kind, so `infoPanel.js` and `cycle.js` do not import each other; `App.goToBuilding()` glides there and opens the panel.

## Data model

* **Map** (`world/map.js`): one `Uint8Array`/`Int32Array` per layer, index `y * w + x`. Persistent layers: terrain, variant, road, aqueduct, rubble, fixedRoad, wall (wall/gate), roadblock (on road tiles: `ROADBLOCK.PRESENT` plus the bits of the walker groups it lets through; missing in older saves, which load without any), bridgeLow (1 on a low bridge's `Road.BRIDGE` tiles; missing in older saves, whose bridges are all ship bridges). Derived layers (rebuilt, never saved): building ids, desirability, water coverage bits, road network ids, distance to water, **navigable** water (connected to the map edge; ships) with `navBody` (which navigable water a tile is, so warships and raider ships never leave theirs) plus `seaEntry`, both split at low bridges (`splitAtLowBridges()`: a low bridge's tiles leave both, and water joined only through them gets a number of its own; the part holding a body's first tile keeps its number, so with no low bridge nothing changes; `navWhole` and `fishWhole` keep the unsplit bodies), and **fishing water** (`fishBody`: every body of water of `FISH_BODY_MIN` tiles or more, labelled); all three closed (0) under a waterside building's rows on the water (`closeBuiltWater`, before the split, so a building and a low bridge closing a channel together split it too; the bodies' sizes, numbers, the sea entry and the grounds come from the terrain alone), worked out again whenever such a building comes or goes (`Game.waterwaysChanged`) and once more as a save loads, after its buildings are down; a boat on a route planned before one went up stops short of it and plans again, as at a new low bridge with its `fishingGrounds` (`computeFishing()`: from the terrain and the saved `variant` bytes only, no random draws, so every map stays as it was and old saves get grounds too).
* **Map generation** (`world/mapgen.js`): `generateMap({ width, height, seed, type, regions })`, a scenario's through `mapOptions(s.map)`. The same options always give the same map. `regions` (the last campaign step's maps) gathers the fields, woods and rocky hills each in a region of its own (`REGION_KINDS`): three centres a third of a turn apart on a ring (`REGION_RING` of the side from the middle), turned to keep them on land, each adding up to `REGION_BONUS` to its resource's noise within `REGION_RADIUS`, with `REGION_SHARES` of the land for each; the draws come from a stream of their own (`${seed}:...:regions`), so maps without regions are as they always were. `info.regions` holds the centres (not saved: a save stores the terrain).
* **Ruins** (`sim/ruins.js`): the rubble layer is only a flag; `game.ruins` maps a rubble tile to what stood there (a building name or a home's level name), why it fell (`RUIN_CAUSES`: fire, wrath, raidFire, riot, collapse, raid, raidWall, and legionFire, legion, legionWall for Caesar's legions) and the month and year. Every tile of a footprint shares one record, cleared tile by tile when the rubble is cleared or built over (`clearRuin`; an undo puts it back). Saves hold one entry per record with the tiles it still covers. Words only: the sim never reads it.
* **Building** (`sim/entities.js`): plain object. `b.def` is the static definition from `data/buildings.js`. Every building has a `turn` (0..3, quarter turns clockwise of its art, chosen with R as it is placed: `planAction(..., turn)`, `placedTurn()`; `turnRule()` says which turn themselves, the waterside buildings and the arch, which stay at 0; until the player presses R for the tool in hand (`Input.handTurned`, cleared by `setTool`), a building held with a road along exactly one side is turned to put its front there (`planAction(..., turn, { auto: true })` asks `roadTurn()`: `(roadSide - frontSide(type)) & 3`, the front being +y, the side `door(ctx, 'left')` draws on, but for `FRONT_SIDE`'s buildings with none; the plan's `autoTurned` says so, and R turns on from the ghost's turn); looks only but for the hippodrome; rubble's `site.turn` keeps it for Rebuild, and the lots a home falls back to or breaks into keep their home's). Kind-specific fields: `house` (tier = housing level 0-20, pop, pantry, service timers (`police`: days of police cover from a prefect), `entBoth` two-show visits, `devolveDays` bad days in a row, `merged` for a 2x2 block of single-tile homes; for crime: `mood` (null while empty), `moodReason`, `moodTarget`, `hungerStreak`, `criminal` 0/1/2; for disease: `diseaseRisk`, `sick` days left), a garden's or statue's `tendedDay` and `careStep` (sim/gardens.js), `noRoadDays`/`noRoadWarned` (days in a row without a road, and whether the one-time message went out), `stock`/`incoming` (storage, markets, workshops), `orders` (granaries and warehouses: per good `'accept'`, `'refuse'` or `'get'`), `emptying` (the Empty switch) and `orderNote` (what the last Get or Empty check found, for the panel), `shows` (venues; one count per kind in `SHOW_KINDS`, the hippodrome's races included), `hasWater`, `fertility`; waterside buildings (`sim/entities.js isWaterside`) stand out over the water: `waterRows` (1 for a 2x2, 2 for a 3x3, `waterRowsFor`; derived from the terrain as placed and as a save loads, `waterRowsSide`; 0 for one wholly on land from an older save) of their front rows on water tiles, the side they face `waterSide`, placement `sim/construction.js checkWaterRows` (the rows as they must lie, `overWaterFit`, then `waterRowsBlocked`: not the sea entry, a fishing ground, a boat, another's berth or a deployed squadron's spot, and never cutting the open water in two, `map.wouldCutWater`); shipyards and wharves: `mooring` (the water tile they use, cached; like a dock's `berth`, the tile just past the front nearest its middle, `shoreWaterAt`; one from an older save keeps its older rule's tile: right at the water's edge, `waterEdge`, or before that the first water found anywhere round it) and `waterSide` (for the art), a wharf's `boatId` and `catches`, a shipyard's `spareId`, `progress`, `boatsBuilt` and `stock`/`incoming` of timber; the fleet's buildings (out over the water, with `berth` and `waterSide` like a dock): a navalia's `stock`/`incoming` of timber, iron and linen, `progress`, `built` and `blocked`, a naval station's `rally`; a fort's or naval station's `service` (the Empire service switch, `sim/battle.js`); a triumphal arch's `axis` (0: its road runs along x, 1: along y; the arch's middle tiles are building tiles that keep `map.road`, the one place a road lies under a building). Houses change footprint as they grow and split; they keep their id (and the anchor tile) when they do.
* **Linked buildings** (the hippodrome, `span: 3` in `data/buildings.js`): Colonia's footprints are square, so the 15 x 5 hippodrome is three 5 x 5 buildings, the `hippodrome` itself (staff, walker, shows, fire and collapse, info panel; its `parts` list the others) and two `hippodrome_part` (no staff, never burn or collapse; `main` points back, `section` 1 or 2 picks their stretch of the track's art). Turned, the row runs along y (turns 1 and 3) and section 0, the rounded end, sits at whichever end the turn takes the art's start to (`spanLayout()`: the row's size and each section's top-left; `spanOrigin()`: the row's top-left from the main section's; every section has the hippodrome's turn and draws its stretch turned). `linkedGroup()` / `mainOf()` in `sim/entities.js`: `removeBuilding()` takes the whole group, `computeAccessRoad()` takes a road beside any section (`footprintRect()`), a roamer passing a section looks after the main one, flames beside a section heat it, a burned or collapsed section leaves rubble over all 75 tiles whose record rebuilds the hippodrome, `planAction()` previews all three (`items[k].part`, with their `type` and art `state`; `items[0].origin` is the whole row) and `applyPlan()` builds them as one (one cost, one undo). The info panel shows the main section for a click on any part.
* **Walker**: plain object with `kind` = `roamer` (wanders serving buildings), `carrier` (goes somewhere and comes back), `traveler` (goes somewhere and vanishes), `ship` (like a traveler, but its path runs over water instead of roads: merchant ships over navigable water, fishing boats over their own fishing water) or `criminal` (protester, thief, rioter: `sim/crime.js`, with `hp` and the `home` it came from). Movement is always "stand on tile (x,y), walk toward (tx,ty), progress 0..1". A walker with `offRoad` (rioters, and prefects chasing them or walking back from a chase) follows a path over open land (`landPath`: A* with roads cheaper and trees dearer) and only plans again when a building or wall appears on it; `held` > 0 freezes a walker for a tick (a prefect and a criminal in a struggle).
* **Unit** (`sim/units.js`): soldiers and raiders (and a native village's villagers, side `native`) are not walkers. They move freely over open land in continuous tile coordinates (tile centers at .5), fight, and are drawn live by `render/militaryArt.js`. `px/py` keep the previous tick's position so the renderer can interpolate. Ships of war are units too, with `naval` in `data/units.js` (`sim/navy.js`, drawn by `render/shipArt.js`): a liburnian has its `station` and berth `slot` (and a `ramCooldown`), a raider ship its `invasion`, `crew` (the warriors still aboard), fire `pots` and `waitTicks` before it sets out; both follow water routes (`path` over their `navBody`). `updateMilitary()` sorts them out of the land lists, so soldiers, raiders, towers and the crime code never see a ship, and runs them in `updateNavy()`. A Roman unit is `trained` or not (`sim/training.js`), and a new liburnian on its way to the Portus has `drill` (its id) and `drillDay`, and moored there training `trainLeft`; a soldier on a trip from his fort to the Campus has the same, and `trainWait` (a soldier's trip in a save before version 28 is ended as it loads: `upgradeSoldierTripsV27`). Nobody is left inside a building placed over him: `applyPlan` (`sim/construction.js`) hands the tiles it built on (buildings and walls) to `makeRoom()` (`sim/makeRoom.js`), which moves each land unit standing there (and each off-road walker) to the nearest tile it may stand on. One sent to a distant battle (`sim/battle.js`) has `away` and `awayTick` while it walks (or sails) out; at the edge it leaves `game.units` and its record (the unit as plain data) travels in `military.battle.sent.men` / `.ships` (or, recalled and turned back, in a `military.recalls` entry) until it comes home and is put back with the same id. Caesar's legionaries (`imperial`, `sim/legion.js`) are enemy units with `legion` (their army's id, never an `invasion`) and `waitTicks` (their turn at the entrance), so raids and legions keep separate counts. A unit's `side` is `rome`, `enemy` (raiders of every people, Caesar's men, rebel gladiators with `revolt`), `wild` (wolves, with `pack` and `prey`, a walker's id) or `native` (native villagers, `attacking` while their village is at war); `hostileToRome(u)` (`sim/combat.js`) is the one rule soldiers, towers and prefects fight by, and only side `enemy` holds up a victory or the peace rating.
* **Reservations**: a cart on its way reserves room at its target (`incoming`; a Get cart reserves room at its own building, from the moment it sets off, for what it will bring back), settlers reserve beds (`house.incoming`), performers reserve a venue slot. `killWalker()` always releases them, so storage never overfills and houses never overbook.

Everything is serializable JSON, see `core/save.js`. Map layers are PackBits run-length coded then base64 (`"pb:..."`, or plain base64 when that is smaller) and walker/soldier paths are packed as 16-bit tile indices (`"u16:..."`; maps are at most 256x256, so every index fits). The save format is versioned (`SAVE_VERSION`, currently 33: 33 games and races (`city.games`: each kind's lift to the city mood, its cooldown and how many were held; `upgradeGamesV32()` starts an older save with none held); 32 marble as a home good from the Marble Villa up (homes and markets hold it; `upgradeMarbleV31()` gives an older save's Peristyle Villas and better six months of it); 31 monuments (a monument's `mon`, a work camp's `camp`, a camp cart's `campClaim` and its reservation at the site; the ledger's `monuments` row, which `upgradeMonumentsV30()` gives an older save's ledgers at 0; a hand-edited monument or camp record missing a part gets a fresh one); 30 waterside buildings stand out over the water (a building's front rows on water tiles, closed to boats; `waterRows` derived from the terrain as it loads, so an older save, whose waterside buildings all stand wholly on land, needs no step: they keep their berths and look; the version moves so an older game refuses a newer save); a prefect at a fire waits with `afterWait` `douse`); `upgradeFireGroupsV27()` ties an older save's burning tiles together by the ruin record they share; 27 festivals cost goods and the gods mind being forgotten (each god's `monthsSinceFestival` and `festivalsHeld`); Until 1.0 a release may refuse older saves (`MIN_SAVE_VERSION`, now 4), always with a readable message; fields added within a version get fresh defaults when missing. Campaign saves store only the mission id plus `difficulty`, so they load with the mission as it is now (its goals, demand and partners; `addNewPartners()` gives a partner the mission has gained since the save was made its route, closed); sandbox saves store their whole scenario.

**Difficulty** (`data/difficulty.js`) is one table of levers per level (funds, risk, production, winter farm growth, immigration, mood, raid size/interval, raider strength, the Emperor's request size/interval/deadline, crime, disease, the favor bands that send Caesar's legions home or halt them, `legionHome` and `legionHalt`, in points, and a monument's upkeep `monumentUpkeep` and Insane's `monumentRaze`). `Game` looks the level up once (`game.difficulty`, from `scenario.difficulty`) and each system reads its own lever; campaign missions get a level through `withDifficulty()` (`data/scenarios.js`), which also scales their funds.

## The genre mechanics, where they live

| Mechanic | File | Short version |

## Rendering (`render/`)

* **Projection**: tile (x, y) top corner at world pixel `((x - y) * 32, (x + y) * 16)`. Camera scale = zoom x devicePixelRatio; everything is drawn in device pixels for crisp art.
* **The view turn** (`view.js`; rendering and input only, the sim never sees it): the city seen from any of four sides, `camera.turn` 0..3 quarter turns clockwise on the screen, the same turn `turn.js` gives building art (turn 1 takes +x to +y). The renderer works in **view tiles**: a W x H map at turn t is a W' x H' map (W and H swap on an odd turn), map point (x, y) going to (x, y), (H - y, x), (W - x, H - y), (y, W - x) at turns 0 to 3 (`toView`, `fromView`, `viewTileOf`), and the projection above applies to view tiles, so world px are the turned view's. The camera maps through it (`mapToWorld`, `worldToMap`, `screenToTile`, `centerOnTile`, `glideToTile`; its bounds are the view map's), and `setTurn()` keeps the map point in the middle of the screen where it is (an instant swap, as the original). The ground pass walks the view's rows and finds each map tile with `tileAxes()` (two multiply-adds, no allocation), so its cost is that of turn 0; `viewTiles` stays a map-space rectangle for the passes that loop over map tiles (`mapRectOfView`; with the camera looking past the edge it stays empty). Depth is the view's x + y (`stripsFor` cuts a building from its footprint's view corner, `viewFoot`; walkers' `walkerWorld(w, alpha, t, W, H).d`; a bridge deck's `bridgeSpan(..., t)`; ghosts by `ghostOrder(items, t, W, H)`). Neighbour masks are worked out on the map and rotated (`rotMask`: N becomes E at turn 1; `rotNibbles` for an aqueduct's links and reservoirs and a blend's edges and corners; `rotBlend`; `viewAxis` for roadblocks, `bridgeLook` for bridges), so a turned tile uses the sprite and key a turn-0 tile of that shape uses: no new ground keys. A building is drawn at its footprint's view corner (`Renderer.footAt`) with its art at `artTurn(b, t)` = `(b.turn + t) & 3`, and so are its flags, altar flame, crowd, stock, kiln smoke, forge sparks and night lights; a hippodrome's races face `raceSpot(..., t)`'s direction. Walkers face their map step turned (`viewDir`; standing, their `lastDir` turned). Soldiers, raiders and ships: the sim's `u.facing` is the unturned screen's, so the renderer keeps each unit's last heading (`Renderer.headings`, render state only) and `unitFace()` turns it: the way it moved, or toward the foe it stands and fights (`u.target`), giving way to the sim's facing when they disagree (a raider turned to strike a building); `drawUnit` and `drawWarship` take that facing, `drawProjectile` the turned velocity. Map gates turn their pillars (`mapGateOffset(..., t)`); tile sides for outlines go through the camera, so overlays, coverage, hints, ranges, the ghost and its footprint, the no-road edges, selection outlines and rally lines all follow. The **minimap** turns with the view (as the original's): it is drawn row by row of the view, so a turned minimap is the unturned minimap of the turned map, the camera frame stays a rectangle and a click maps straight to world px; an N marks north. North is the game's compass (`sim/combat.js screenDirection`: straight up at turn 0, the map's (0, 0) corner), which the top bar's needle (`Hud.showViewTurn`) also shows. Input: `Q` / `]` and `Shift+Q` / `[`, the top bar's buttons and the console's `view` call `App.turnView()` (a held key turns once), which turns the renderer and calls `Input.rehover()` (the tile under a still cursor changed); scrolling stays screen-relative. The turn is saved with the camera state (`Camera.serialize()`'s `turn`; a save without it opens at 0) and `Renderer.attach()` starts every game unturned; nothing in the sim depends on it (`tests/view.test.mjs` checks a game is unchanged by turning).
* **Zoom levels per renderer** (`config.js`, `Camera.setLevels`): Classic has five, `ZOOM_LEVELS` 0.5 / 0.75 / 1 / 1.5 / 2; the WebGL back end has `ZOOM_LEVELS_3D`, the same five then 3 / 4 / 6, to see the models up close (it hands them to the camera through `zoomLevels`, `Renderer.setBackend`). A level's index means the same zoom under both, so a save keeps only `zoomIndex` and stays readable by either: a level the renderer lacks becomes its closest, at once, the middle of the screen kept (`setLevels` when the player goes back to Classic from 4x; `restore` when a save made at 4x opens in Classic, working out the saved view's middle from the zoom its index stood for). 6x was kept after screenshots on the GPU: the models hold up there (the well's puteal, the fountains' basins, the market's pavilion, the forum's columns, the granary's and the warehouse's walls), the frame costs what 2x does, and sprites stretched twice still read as the flat art they are. Keyboard (`+` / `-`), wheel and pinch all go through `zoomStep`, so they reach every level; panning by keys, the screen's edge and dragging is in CSS px, so it keeps its feel on screen at any zoom (slower over the map up close, as it should be).
* **Camera** (`camera.js`): `zoomIndex` is the zoom level the player picked; `zoomF` is the zoom shown, which eases to the level in about 0.2 s with the point under the cursor pinned. Also a fling (drag velocity that decays) and `glideToTile` (eased travel, used by messages, advisors, the minimap and Home). `centerOnTile` and setting `zoomIndex` stay instant (loads, tests). `smooth = false` (reduced motion) makes everything instant. `update(dt)` runs once per frame from the renderer.
* **Sprites**: every piece of art is a `spec` (size, anchor, draw function) rendered once per zoom level into an offscreen canvas (`sprites.js`). Art is procedural (`terrainArt.js`, `buildingArt.js`) using the tiny iso kit in `draw.js` (boxes with wall texture and contact shadows, tiled roofs with eave shadows, columns, windows with optional shutters and flower boxes, trees). Sprites are made for the zoom LEVEL and remember their scale `s`; while a zoom eases, `blit()` stretches them by `scale / s` (building strips snap to whole pixels so they do not show seams). New sprites get about 8 ms per frame (`spriteBudgetMs`); past that the cache borrows the other kept zoom level's copy, so a zoom never stalls while hundreds of sprites are drawn, and they sharpen over the next few frames. **Scale cap**: a sprite is drawn at `min(zoom x pixel ratio, SPRITE_SCALE_MAX)` (6 device px a world px: `Camera.spriteScale`), never capped under Classic (its closest, 2x at a pixel ratio of 2, is 4); past it, at WebGL's 4x and 6x, the sprite is stretched by `scale / s` as while a zoom eases, smoothly (linear filtering). A sprite's memory grows with the square of its scale (`SpriteCache.bytes` counts it; the performance readout shows it with the zoom): on the Large demo city (demo 3, 120 days, the farms) after looking over the whole town, 38 MB at 2x, 85 MB at 3x to 6x (at a pixel ratio of 2 one scale for all three, so going between them redraws nothing; at 1 they are drawn at 3, 4 and 6); a cap of 8 measured 151 MB for edges a little crisper at 4x and 6x. At a new zoom the sprites in view are made in one frame of 2 to 5 ms (the 8 ms budget is not reached: few sprites are in view up close). **Cover sprites**: a building drawn as a 3D model still needs its sprite, only to read what hides a figure behind it and where its sign stands, both in world px; it is made in its own small cache at one world px a pixel (`Renderer.coverSprites`, on the same time budget and look change as the main one), never at the zoom's scale (a farm's was 3.5 MB at 6x): 145 MB of the city's sprites at 6x before, 85 after; 64 MB at 2x before, 38 after.
* **Draw calls**: keep them down in the per-tile passes. Chromium flushes a canvas mid-frame past a few thousand draw calls, which roughly doubled the frame time when zoomed out, so edge blends are painted into the ground tile's sprite (`groundBlendSpec`) instead of drawn as a second sprite. Test zoomed-out views (`zoom=0`) after adding anything per tile. Turning the view adds no draw calls: with the whole Large map on screen at the widest zoom (4200 x 2200, the demo city, so every turn draws the same things) a frame took 94.8 ms unturned (94.5 before the view could turn) and 95.0 to 95.8 ms at turns 1 to 3 when it came in. On a 1600 x 900 screen the odd turns frame a differently shaped piece of the map (a quarter turn of the tiles is not one of the screen), so they can hold more objects and cost more for that alone (22.8 ms unturned, 23.3 to 24.1 ms turned, on Large).
* **Collection and back ends** (`items.js`, `canvasBackend.js`, `render3d/`): `Renderer.render()` works out what to draw and a back end draws it, told in this order each frame: `begin()`; the ground in the view's rows (`ground(spr, wx, wy)`, an overlay's tint `groundFill`, a sun glint `groundLive(draw, box)`); building shadows (`fill(pts, color)`); the sorted items (`items(list)`: `K_STRIP` sprites with their depth `d`, strip `j` of `n` and alpha, and the kinds painted live each frame, which `Renderer.drawLive(ctx, it)` paints onto whatever 2D context it is given); buildings with a 3D model (`model(b, place)`, only where `hasModel(type)` says so); then, for a back end that composes (WebGL), `post(layers)` with what lies over the scene and under the night (particles, gulls, cloud puffs, flocks, the night's tint and lights, the lightning's flash); then `present()`. With Classic, the renderer paints those itself on #view after the scene, as it always did. The rest (the weather's drops and flakes, signs, tool previews, coverage and outlines) the renderer paints on its 2D context: #view's with Classic, the transparent overlay canvas's with WebGL (see "Composition, render scale and the performance readout"). Both back ends place a sprite through `spriteRect()` (device px: whole pixels 1:1, or stretched with strips snapped to whole pixels), so a sprite lands on the same pixels either way. A back end whose `drawsGround` is true this frame (the WebGL one with its 3D ground, see "The 3D ground") draws the ground itself: the renderer then leaves out the ground's sprites (terrain, shores, roads, plazas, rubble, sun glints) but still tells it the overlay tints and building shadows, and leaves out the 2D shadow of a building whose model casts a real one (`modelShadows`). The Classic back end (`canvasBackend.js`, the default) is the old drawing call for call: its picture is pixel-identical to v0.19.13's (12 views: four view turns by day and night, the widest and closest zoom, an overlay, a selected fort). `Renderer.setBackend()` swaps them (`App.applyRenderer()`: Settings > Renderer, or `?renderer=3d`); `Renderer.be` is the one drawing this frame, the Classic one while WebGL cannot (`ready` false); `stats.backend` says which.
* **The WebGL back end** (`render3d/webglBackend.js`, three.js, beta): every sprite is a textured quad on the device px `spriteRect()` gives. A sprite's canvas is uploaded once as a texture and freed when the sprite cache lets the sprite go (`SpriteCache.onDrop`: a zoom level dropped, last month's look, a snow level, `clear()` on a pixel ratio change). What is painted live each frame is painted by the same functions into a cell of one live-art texture (`liveBox.js` sizes each cell from the art's measured reach; only the rows used are uploaded), drawn as a quad in its place in the order; fills are triangles. Quads are batched in the painter's order, up to 16 textures a draw call (a slot per vertex, the fragment shader picks the texture; an atlas of all sprites would make it one call, not needed yet: 113 to 325 draw calls a frame on a 1600 x 900 screen, 1,697 for the whole Uber map). The camera (`projection.js aimCamera`) is a real orthographic three.js camera framing exactly the 2D camera's world px rectangle at its scale: turned 45 degrees about the vertical and looking down at the angle whose sine is HALF_H / HALF_W (30 degrees), in a 3D world of the VIEW's tiles (x = u, z = v, y up), so a view turn needs no camera move and `screenToTile`, `toScreen` and picking are untouched. Colors pass as bytes (three.js's color management off, no output conversion; textures premultiplied and blended ONE, ONE_MINUS_SRC_ALPHA, as the 2D canvas blends). Its canvas is on the page under the renderer's 2D overlay and #view (`Renderer.mountLayers`); until v0.20.8 `present()` copied its picture onto the 2D canvas every frame instead. A lost context (`webglcontextlost`) hands the drawing to Classic until `webglcontextrestored`. Against Classic the picture differs by 1 level of rounding on blended shadows and tints and on antialiased edges (0.6 to 8% of pixels, nearly all by 1) and in the models. Frame times, headless (`stats.drawCalls`, `textures`, `live`, `liveTexture` count its work): on a GPU (RTX 5060 Ti, D3D11), Large map at 1600 x 900, Classic 16.7 / 38.8 / 16.7 ms a frame at 1x / 0.5x / 2x and WebGL 16.6 in all three; the whole Large map at 0.5x on 4200 x 2200 113.5 ms against 16.6, Uber 230.7 against 28.8. Under SwiftShader (software WebGL, as in CI) every WebGL frame pays a software GPU's fixed costs: 50 to 150 ms at 1600 x 900 against Classic's 17 to 100, though the whole Large map is still faster (77.7 against 306.7 ms).
* **Depth with 3D models**: models are drawn first (see "The look lab's models in the game"), with the depth buffer on; then the quads in the painter's order, each tested against the depth the models wrote but writing none. Among themselves quads keep the 2D order exactly; a model hides what is behind it pixel by pixel, and what is in front of it is blended over it. Sprites and models share one depth measure (`projection.js`): D = u + v + z / 48 tiles for a point of the view z px up (the 2D renderer's x + y on the ground, nearer the higher). Ground quads lie on the ground (`groundDepth`, a little further back, so a tile never paints over a model's foot); the other quads stand up like cardboard cutouts on the ground line of their sort depth `d` (`standDepth`), so a walker in front of a tall model is in front of it at every height of his figure and one behind it is hidden.
* **3D models**: see "The look lab's models in the game" below: the well and the fountain are the lab's models, instanced, at a level of detail by the zoom, in the 3D ground's light. A modelled building's sprite is still made and its strips kept in `coverStrips` (not drawn): a figure behind it is hidden where the sprite would be, and the building is picked by its footprint (`app.js clickTile`) as always. The night and the weather's tint and its signs apply as to a sprite; its 2D shadow too, except at Ground High, where it casts its real one.
* **Depth sorting**: flat things (terrain, roads, rubble) draw first. Everything tall is sorted by the x + y of its front point (in view tiles: the painter's order turns with the view). Multi-tile buildings are cut into half-tile-wide vertical **strips**, each sorted by the front-most footprint tile it covers. That is what lets a walker pass correctly in front of and behind a colosseum with a simple sort. A strip is a whole screen column of the sprite (back walls, yard and front walls in one), so a soldier in his fort's yard is drawn just after the fort's last strip (`Renderer.yardDepth()`, before its flag cloth); his yard spot keeps him clear of the walls in front of him.
* **Picking figures** (`pickWalker`, `pickUnit`): each frame keeps where every walker and land unit was drawn and at what depth (`walkerSpots`, `unitSpots`, with `d`) and the building strip items it drew (`coverStrips`: sprite, anchor, strip j of n and depth). A click finds the figures whose box holds the point, and one is hidden there only if a building strip drawn after him (a greater depth) is opaque at that pixel (`coverDepthAt()`: the strip's own column, the sprite pixel that `blit`/`blitStrip` put there at any zoom or view turn, alpha 128 or more, read with `getImageData` on the sprite's canvas). Pixels are read only on a click, for the first figure that asks, never per frame. Before, a building was a box as tall as its sprite over its whole footprint, flag poles and all, and hid figures standing in plain view beside it. Ships of war are picked by `pickShip` (no cover test: a hull click wins over the building on that tile).
* **Overlays** (`overlays.js`): tile tints and info columns; non-relevant buildings drawn as flat footprints. The crime overlay's columns and words come from `ui/crimeInfo.js`, the health overlay's (disease risk, sick homes in `SICK_COLOR`) from `ui/healthInfo.js`; the Problems overlay (`ui/problems.js`) puts sick homes and homes in unrest ahead of what a home lacks.
* **Turned art** (`turn.js`): any building can be drawn turned 0 to 3 quarter turns clockwise (turn 1 takes the art's +u edge to +v), a pure function of its art and the turn, so the view rotation can draw a building at `(b.turn + view turn) & 3` with no art of its own. Art is still written for turn 0, back to front. `buildingSpec(..., turn)` draws through `drawTurned()`: at turn 0 it draws straight onto the canvas as it always did; turned, `P()` and the primitives turn (u, v) inside the footprint (`turnUV`), `box()` and the roofs turn their rectangle and draw the faces seen after the turn (an odd turn swaps a gable's ridge axis), `windows()` show on the seen face of their axis (a wall's windows run all round it), and `door()` stays where it is: turned away it is drawn on the hidden face, under the walls, and records no night light. Meanwhile the canvas is a recorder (`TurnRecorder`): every paint call is kept with its state and path in **units** (one primitive each, or the direct canvas calls that follow the `P()` points that placed them, as tall as 12 px unless they lie flat on one wall), each with its box in turned (u, v, z); `sortUnits()` orders them back to front (A first when it lies wholly on the far side of B along u or v, or below it along z; units apart on the screen are left alone; two that overlap keep their drawing order, unless one is a face (`decal()`, or a flat vertical polygon), which goes in front of what is on its inner side and behind what is on its outer side once it looks away), then the recording is replayed onto the canvas. Hand fixes for art that assumed its facing: a gable's pediment and its emblem, the arch's face and the big statue's inscription are `decal()` faces; the theater's bowl is drawn through footprint points; the iron mine's hill has its far sides; the ranch fence goes rail by rail; a 2x2 block of homes draws each home in its own square (`withOrigin()`); round or square-symmetric buildings (`SAME_EVERY_WAY`: the well, fountain, reservoir, arenas, oracle and small statue) draw as written at any turn. Live details turn too: flags (`flagsFor(type, size, turn)`), the altar flame (`templeAltar(S, turn)`), kiln smoke and forge sparks, the theater's crowd, night windows and torches (`lightsOf(..., turn)`), and the warehouse's and granary's stock (`drawTurnedOver()`: the stock and the building's own walls, recorded once per type, turn and snow, sorted together; only the stock is painted, each piece followed by the walls in front of it that overlap it, so a wall in front covers it again and nothing translucent is painted twice). Round buildings' night torches stay put (`lightsOf` uses turn 0 for `SAME_EVERY_WAY`), and a hippodrome's ghost is drawn back to front (`ghostOrder()`). The races are laid on the turned track by `raceSpot()`. `tests/e2e/artsheet.html?turns=1` shows every building and home level at the four turns (`turns=temple,farm` for some kinds, `snow=1` under snow) and the whole hippodrome each way.
* **Building sprite keys** are `b:{type}:{size}:{variant}:{state}` (`buildingKey()` in `renderer.js`; `state` from `artState()`: a home's level, a farm's growth, a garden's or statue's 1 once its care is down to 60% or less (`NEGLECT_STEP`; drawn dry and dull, `neglectTint()`)...), then `:t{turn}` for a building drawn turned (`turnKey()` of `artTurn(b, view turn)`, its own turn plus the view's; nothing at 0, so unturned keys are as they always were, and a building turned 3 seen at view turn 1 shares the unturned sprite), then `:sick` for a sick home (drawn a little pale with a pale cloth on a pole, `sickSign()` in `buildingArt.js`), then the snow suffix `~n{level}`, which stays last so a look change can drop sprites by suffix.
* **Fishing and races** (looks only): a fishing boat (`drawFishingBoat()`) shows its state (sail up under way, the net cast with a ring of floats while fishing, a basket of fish on the way home); gulls over each fishing ground (`drawGulls()` in `waterArt.js`, `Renderer.drawFishingGrounds()`, drawn still with reduced motion). The hippodrome's three sprites share one design (`hippodromeArt.js`, state = section). While races run, three chariots lap the spina (`Renderer.raceItems()`): each is queued just after the strip of its section's sprite that holds it (strips are screen columns drawn at their front tile's depth), or the track would paint over it. The charioteer and a chariot maker's team are drawn as a chariot and pair (`drawChariot()`). The shipyard's art state is its water side plus the hull on the slip (none, ribs, planked); the wharf's its water side plus baskets of fish while it holds a catch.
* **Walkers** are drawn live each frame (`walkerArt.js`), not cached, so they have no sprite keys. A walker type's `item` picks what it carries; the criminals have their own: a protester shakes a `placard`, a hooded thief carries a `sack`, a rioter waves a flickering `torch` (the raised arms bob with the clock, visual only).
* **Carts** show their cargo (`render/cargoArt.js`): each good has its own item (sacks of wheat, crates of vegetables and fruit, baskets of olives and grapes, joints of meat, clay lumps, logs, iron ingots, marble blocks, pots, pale oil and dark wine amphorae, tables and chairs, shields with spears, sheaves of arrows, bundles of flax with blue flowers at their heads, bolts of linen, stacks of folded clothes in two dyes) in a `layout` (`pile`, `row` or `layers`); a good missing from `CARGO_ART` gets a block in its `GOODS` color. The load shows as 1 to 4 items against what the cart holds (`cargoLevel`), and what it holds depends on who sent it (`cartCapacity`: a farm's wagon `FARM_CART_LOAD`, a warehouse's single lot `CART_CAPACITY`, everyone else `CART_LOAD`), so the renderer passes the sending building's def to `drawWalker`. A farm's cart is a longer four-wheeled wagon drawn by an ox; horses (`LED_GOODS`) are led on a rope behind the drover, one per 100 units, and a ranch's drover walks home with only the rope. A caravan's mule carries plain bales on its way in and, on its way out, the goods it bought (`walker.packs`, set by `caravanArrive()`; art only, the sim never reads it; saved with the walker, and a save without it just shows bales). All of it is a few shapes per item, drawn live; `tests/e2e/artsheet.html?carts=1` shows every good at two loads, both facings.
* **Life in the picture** (visual only, never touches the sim): buildings cast soft shadows to the lower right (drawn after the ground, before objects; `shadowLength()` in `buildingArt.js`); new buildings rise out of the ground with a dust puff; forests sway using 5 cached wind frames whose phase rolls across the map; water glints; working fountains spray; fires glow and throw embers; homes smoke; smithies throw sparks. `ambient.js` draws drifting cloud shadows and passing birds. Settings can turn the ambient layer off, and the OS reduced-motion preference disables all decorative motion.
* **Live details** (`liveArt.js`): drawn every frame on top of their building as `K_EXTRA` items right after its strips: flag cloth (the sprite only has the poles when drawn with `live = true`; `FLAG_SPECS` in `buildingArt.js` lists every flag), shoppers along the front of a stocked market, spectators in theaters and arenas while a show is booked (seats hidden by the stage or the arena floor are skipped), the temple altar fire.
* **Terrain**: 8 ground variants per land type. Where two kinds of ground meet, a wavy fringe of the stronger one (forest floor > grass > meadow > sand > rock, `BLEND_RANK`) is painted onto the weaker tile. The packed blend code per tile is cached (`Renderer.blendAt`) until `map.revision` changes.
* **Order of a frame** (the same with either back end; with WebGL everything up to the flash is drawn on the GPU, the rest on the 2D overlay): ground, building shadows, sorted objects, particles, cloud shade and birds, then the **night** (`lighting.js`: the scene is multiplied by a half-resolution light map filled with the sky tint plus warm pools of light, then window/torch/fire glows are added), then **rain/snow/lightning** (`weather.js`), then the red **no-road signs** (`drawNoRoadSign()` in `liveArt.js`, over every building in view for which `lacksRoad()` holds; never smaller than its zoom-1 size, about 20 CSS px across, shown under overlays too; `stats.noRoad` counts them), then tool previews, radius hints and selection outlines, so those are never darkened. A building ghost on a spot with no road it could use is drawn in the warning color (its own sprite key, `...:noroad`, before the snow suffix; `tintedSpec()`), with the edge tiles where a road would serve it picked out (`accessEdgeTiles()`; `stats.ghostNoRoad`, `stats.roadEdges`), and `ui.js` puts the warning by the cursor in the tooltip's `warn` style.
* **Day, season, weather** are derived per frame in `Renderer.updateEnvironment()`: time of day from `game.time.totalTicks` (`dayTime`, `DAY_TICKS`), the season palette from `game.time.month` and the snow cover level (`seasonPalette(month, snow)`; `MONTH_LOOK` places each month among the four looks, and ground/tree/blend sprite keys end in `~p{look}[n{snow level}]`, building and rock keys in `~n{level}` while snow lies), and the weather state machine advanced by the game ticks that passed (so it pauses with the game). Seasons are calendar data (`sim/time.js` `seasonOf`, `SEASON_NAMES`, `GameTime.season()`; Dec-Feb winter, Mar-May spring, Jun-Aug summer, Sep-Nov fall); `weather.js` re-exports them. The weather draws a new spell when the season changes and `seasonalKind()` keeps rain and storms out of winter and snow out of the other seasons; `Renderer.attach()` calls `weather.reset()` so a new or loaded game opens clear and without snow. Snow **cover** (`weather.cover`, 0..1) builds while it snows and melts after (slowly in winter, fast in spring); it is quantized to `coverLevel` 0..3 with a little hysteresis, and the art bakes it into the sprites (white ground, snow-capped trees and rocks, snow on roofs via `setRoofSnow()` in `draw.js`, white fields), so there are no extra draws per frame. A **look change** (new month or snow level) is prepared, then swapped: `SpriteCache.get(key, spec, fallback)` keeps returning the old look's sprite while the new one is drawn within a 4 ms budget per frame (`pending` counts what is missing); the first frame that ends with nothing pending drops the old sprites (`finishLookChange`), so the next frame shows the new look whole. When changes overlap (snow deepening again before the last level is ready), `lookStep()` keeps the complete old look as the stand-in and drops the half-made one. A new or loaded game switches at once (`lookHard`). Window positions for night lights come from the art itself: `draw.js` records where `windows()` and `door()` put openings when the art is drawn into `recordingContext()`.
* **Coverage hints**: clicking a well/fountain/reservoir, or placing one, paints its supply area (dark blue) over the area already covered by that kind (pale blue, read from the sim's water layer). **Water hints** (`waterHintLayers`): while a tool is in hand, the water already there is tinted faintly under everything else: with the Housing tool, well water (palest) and fountain water (a stronger blue); with a building that needs piped water (fountain, baths), the reservoirs' piped area. Each tile is filled once with its strongest layer, each layer gets a thin outline, and tiles the coverage preview paints are left to it (`drawWaterHints`, counts in `stats.waterHint`).
* **Bridges** (`bridgeProfile.js`, `terrainArt.js` `bridgeSpec`, `bridgeFootSpec`, `lowBridgeSpec`): the deck's height along a run of bridge tiles comes from the map alone (`bridgeProfile()`: the run scanned each way along `bridgeAxis()`, which a bridge neighbour decides before any road does). The ship bridge stands `BRIDGE_DECK_Z` (33 px) over the water, over a merchantman's mast (the deck's width and far parapet hide 13 px more than its height; a test measures the ships' art against it), and climbs from each bank on a ramp 1.5 tiles long: from the middle of the bank's road tile (its foot, `bridgeFeet()`, drawn on that road tile, so a road joining there from the side meets it at road level) to the far edge of the first water tile. A bank tile with a gate, an aqueduct, a roadblock or a building keeps its look and the ramp starts at the water's edge instead; a run that ends at more water stays up. A junction is a level landing the ramps climb from at their usual slope (`runOf()` holds, `crossings()`): a road on land beside a run's first or last tile (a shore road at a lake's corner, the Imperial road leaving its last water tile sideways) holds that tile at road level, and a tile where two bridges cross (a neighbour across it running the other way; one alongside running the same way is no crossing) is held at the lower of the two decks over it, so both runs meet it level; such a level tile leaves out its parapet on the joining side and runs its deck to the tile's edge (`bridgeLook().open`, `bridgeSpec` `open`). The low bridge (`LOW_BRIDGE_DECK_Z`, 5 px) climbs over the first and last half tile of water. Each tile is drawn with its deck's heights at its near edge, middle and far edge, ordered as the view turn sees them (`bridgeLook()`), and `bridgeSpan()` lifts anyone on it by those same heights read between the three points (`deckLift()`), so feet stay on the deck on a ramp at every turn. A ship bridge tile draws the pier at its far end (+t in the view): the near pier is the previous tile's, drawn earlier, so a ship under the tile (drawn just before its deck) shows in front of the near pier and behind the far one, its hull through the arch and its mast behind the deck. Over a ramp a mast would stick up through the bridge, so a ship under a deck is drawn clipped (`mastClip()`, `Renderer.clipTo()`): cut where the deck over it is, as if its mast were struck, and never above the bridge's far parapet. The strike takes the first fifth of a tile past the far edge (the cut comes down from over the masthead, so the mast sinks behind the far parapet), and once the ship's middle is past the near face it is drawn in two pieces: the hull behind the face's plane before the deck, the rest after it (`SHIP_IN_FRONT`), cut first at the arch's crown and rising clear of the mast before it leaves the tile. A fort's rally standard on a bridge stands on the deck with its men (a station's flag stays on the water). The run's first tile in the view draws its own near support. Sprite keys: `br{axis}{h0}.{hm}.{h1}[a][o{open}]` (ship bridge, `a` for that support, `o` with the open sides: 1 far, 2 near), `brf{axis}{+|-}{h}` (a foot, climbing toward the front or the back of the view), both with the snow suffix `~n{level}` (snow caps the parapets and cutwaters; the deck stays clear like the roads), and `brl{axis}{h0}.{hm}.{h1}` (low bridge, no snow).
* **Aqueducts** (`terrainArt.js` `aqueductSpec`): cached sprites keyed by their connection mask (`aqueductMaskAt`: the low four bits are the connections, the next four mark which of them are reservoirs, where the channel steps down to the rim) and by whether the tile is a road (a straight aqueduct over a road is drawn as a bridge with one wide arch).
* **Temples** (`buildingArt.js` `TEMPLE_LOOKS`): one look per god (roof, walls, pediment and emblem, a piece in front). The pediment is the god's color (`GODS[g].color`, which its priests wear), and no two roofs or pediments are near the same color (a test holds them apart), so the five read apart in the build menu's small icons.
* **Military layer** (`militaryArt.js`): walls/gates are cached sprites keyed by their neighbor mask (like aqueducts; the WebGL back end draws them as 3D models instead: see "The town walls in the game"); soldiers, raiders, arrows, sling stones, fire pots and rally flags are drawn live each frame and depth-sorted with everything else. Ships of war (`shipArt.js`: the liburnian's two banks of oars stroke with the distance rowed, its sail furled in battle and at rest; the raider ship shows the warriors still aboard) are drawn the same way; the renderer keeps where each was drawn (`shipSpots`) so a click picks one (`pickShip`) for its panel. A selected naval station shows the water its squadron guards (`drawSeaGuard`). The Navalia and the Naval Station are cached sprites (`navyArt.js`), turned to the water like the dock (`state` = `waterSide`, plus the hull on the navalia's slip). A waterside building out over the water adds `OVER_WATER_ART` (16) to its art state and is drawn by its own pier art (`dockQuayArt`, `wharfPierArt`, `shipyardPierArt`, `navaliaPierArt`, `stationPierArt`, `portusPierArt`): its rows on the water as a deck on timber piles or stone piers (`waterArt.js pierDeck`, boxes, so every view turn orders them) with the renderer's water tiles showing under and between them; one wholly on land from an older save keeps its old drawing. Caesar's legionaries are drawn as Roman soldiers (armor, helmet, the legionary's shield and sword) in purple with a white plume, never with the raiders' hair, over the enemy's red shadow. A triumphal arch (`triumphalArchArt`, `state` = `axis`) leaves its middle strip unpainted so the road drawn on the ground shows through, with the piers either side, the attic and its gilded team on top, the vault's curve on the face the road comes out of.
* **Rally flags** (a deployed fort's standard, a deployed station's flag): the renderer keeps where each was drawn (`flagSpots`), and `pickFlag` finds the one under a screen point by the standard's own shape, never smaller than about 12 x 30 CSS px. `input.js` asks it first on a left press with no tool and no deploy pick (only a ship's hull, `pickShip(.., true)`, wins over it), so a flag beats the soldiers, walkers and buildings under it; the press is then a flag press (`input.flag`), never a pan: released within the click slop it opens the fort (`app.clickFlag`), moved further it sets `renderer.flagDrag` ({ id, x, y }: the map tile under the pointer, recomputed each frame so keys and zoom keep it true), and the renderer fades the flag where it stands and draws the ghost standard (`drawGhostStandard`, red where `rallyTarget` says no) where it would go. Let go over the canvas (`overCanvas`: not over a panel) it calls `app.dropFlag`; Esc, a second finger or a cancelled pointer drops nothing. A fort's number is drawn over its standard (`drawStandardNumber`, left out zoomed far out).
* **Empire map** (`ui/empireMap.js` draws it, `ui/empire.js` is the full screen): one renderer for the Trade advisor's small map (a snapshot) and the Empire screen (redrawn every frame), in a 100 x 60 map-unit space. The geography is `data/empireGeo.js`: coasts, islands, gulfs, rivers, mountain rows and region names written as longitude and latitude and projected equirectangularly (10 W to 37 E, 48 N to 26.5 N, so a degree of longitude is about 0.76 of one of latitude, true near 40 N); `at(lon, lat)` places a city (`pos` in `TRADE_PARTNERS`, `SITES`, `ROME_POS` all use it) and `isLand(p)` answers land or water by point in polygon (the sea ring less the islands, plus the Red Sea gulfs and lakes). Each partner's route comes from `routePath(site, id)` (`data/empireRoutes.js`: the shortest way over the roads or lanes from the province's site, drawn as a curve), which keeps caravans on land and ships on water; a test walks every curve of every mission's site and every sandbox site, and the star is drawn at the site (`homeSiteId`). Names are placed last (`placeLabels`): each on the first side of its marker where it hits no other name or marker. Travelers are read from timers the sim already keeps, never simulated: `empireTravelers(game)` puts a caravan or ship on its route for the last `shownTripDays` before the route's `nextVisit` (its `tripDays`, at least 2, never more than the shortest gap between visits, so a route has at most one traveler out), positioned by the share of the trip done along the curve, with the day's fraction from `time.tick` so it glides. Until a route's first trader has called (`visits` 0) it is shown over `firstVisitDays` (`sim/trade.js`): that trader set out the day the route opened, so it starts at its city rather than partway along. A warband closes in over the `RUMOUR_MONTHS` (6) before `nextRaidMonth`: while only rumoured (`warnStage` 1, no `warned`) from the site's `frontier` (`frontierDir`) with no number, once scouted (`military.warned`) from its compass side, half way in at the scouts' report (one coming by sea, `warned.sea`, sails in a longship on the nearest side round from it whose whole way in is sea; one by land walks on the nearest side whose way in is all land; from a little nearer where no side is: `warbandPoint(site, dir, frac, sea)`); raiders in the province show beside the city, as do Caesar's legions camped there, each on the first spot over land (`markerSpots(site)`). Armies (`empireArmies(game)`): Caesar's legions on the road from Rome to just short of the province (`legionRoad(site)`, along the roads) by the share of their countdown gone (`legionSummary`), then beside it while on the map; a distant battle's threatened city (`drawBattleCity`), the enemy on its straight line (`enemyLine`) by `enemyToGo`, and the province's troops on their way (`marchLine` smoothed, gliding toward next month's place) or home (`homeIn` of `homeTotal`), from `battleSummary` (`sim/battle.js`). It is pure (tested in node: `tests/empire.test.mjs`, including that reading it changes no state). A message with `empire` (a traveler kind) opens the screen with that traveler picked out (`EmpireView.focus`: hovered, so ringed and read out) instead of gliding to a tile (`ui/messages.js openMessage`). Figures and labels grow on small canvases (`figureScale`) and clicks are tested against the middle of a figure as drawn (`figureCenter`). The screen is modal kind `empire`: like the Advisors the game runs behind it and the keyboard shortcuts work (`App.blockingModal`); its side panel sections are rebuilt only when their text changes, and not while a press inside the panel is held (the days tick by every second or two, and a button rebuilt between press and release would never get its click).
* **Map gates** (`liveArt.js` `drawMapGate`, `K_GATE` items): a stone gateway over the Imperial road at `map.entry` (green pennants) and `map.exit` (red), with torches at night. Mapgen lays the road straight in from the edge for `ROAD_STUB` tiles at each end, so `map.entryDir` / `map.exitDir` (saved with the map) always point straight in and the gates face the edge; `mapGateOffset()` stands the pillars across the road (older saves work the direction out from the roads around the tile); each gate is two items (back pillar, then lintel and front pillar) so walkers pass between them.

## The look lab and the 3D look

The bar for the 3D art is set on one building before any of it goes into the game: the public well in a Pompeian street, drawn as the WebGL back end should one day draw the city. `node scripts/build.mjs --lab --out <file>` builds `src/dev/lab.js` into `src/dev/lab.html`: one self-contained page (three.js and its addons bundled, about 770 KB, nothing fetched), which works on a phone and can be shared as a claude.ai artifact. The game's build does not include the lab; the game's WebGL back end uses the look for its ground (see "The 3D ground") and draws the lab's well and fountain in its materials (see "The look lab's models in the game").

* **The picture** (`render3d/look.js`): linear light, sRGB output and ACES filmic tone mapping (AgX was tried: it turned the warm stone grey-green). A sun (or the moon) with a 4096 shadow map over a tight box round the scene (soft PCF, Vogel disk); the sky as image-based light: three's `Sky` (Preetham's daylight model, with its clouds) or a gradient night sky, plus a warm ground disc for the light bounced from below (without it, a blue dome alone lights the shade and every warm stone goes green), rendered into a PMREM environment. The post chain: GTAO rendered first (its result is a texture the materials read), the scene into a 4x MSAA target, bloom (only what is far brighter than daylight: the flames, the lantern), tone mapping, a colour grade (contrast, saturation, lift and gain, vignette, half a step of dither against banding), SMAA. `MOODS` holds day, golden hour, night and winter in one table: sun, sky, bounce, environment strength, exposure, backdrop, bloom, grade, lamps, snow and wet, the grass tint. `gameCamera()` is the game's own view in metres (a tile is 4 m): orthographic, 30 degrees down and turned 45 as `projection.js`, a tile `TILE_LEN * zoom` px along the screen as a sprite (tested at zoom 2 and 4), turned by quarter turns. The sun turns with the view, as the 2D art keeps its light at the upper left at every turn.
* **Materials** (`render3d/materials.js`): physically based materials shared by key, each on a procedural surface (`surfaces.js`: limestone, travertine, basalt paving, tufa, cocciopesto, plaster, oak, bronze, iron, earth, rope, wool, terracotta, water ripples, the grey lava of a plain fountain's slabs, white marble), painted from noise on the GPU (`paint/`: periodic gradient noise, Voronoi cells with the true distance to their borders, height fields, normal maps by Sobel, cavity) as tiling albedo, normal and occlusion/roughness/metalness textures. UVs are in metres and each surface says how many metres one repeat covers. Every material carries one shader patch (`patchLook`, one program key for all: what differs between materials, the snow that sticks, the wetness, the grass's sway, a town wall's textures read at the world's metres (`worldUV`), is in uniforms, never defines; a material without a surface takes 1 x 1 maps, water and ice the same features, so the well's street is three programs and the flame's): the screen-space AO darkens the sky's and the environment's light and only a third of the sun's (AO on direct light is what makes SSAO look dirty); snow settles by the facing of the shaded surface, broken by world noise, thicker in nooks (dark AO), never on overhangs, filling joints (it cancels the texture's occlusion under it), in patches where little sticks (`snow` per material: a trodden street 0.6); stone darkens where wet; grass sways, turns to straw and sinks in winter; the world fades into the backdrop on a square past the patch (a diamond on screen, like a piece of the game's map). The textures are painted on the GPU before the first frame (see "How textures are made").
* **The warm-up** (`look.warm`, `warmLook`): on a cold GPU cache compiling programs is most of a start (ANGLE's D3D11 takes a few hundred milliseconds for a lit material's), and a program compiled at its first draw stalls the page. So every program a frame needs is compiled at once, in the background (`compileAsync`, KHR_parallel_shader_compile, ANGLE's threads side by side), before the first frame: a dry run of the composer whose `renderer.render` compiles instead of drawing, so each pass's materials compile under the very target it draws into (a program depends on it: linear or the screen, tone mapped or not; compiled for the screen, the scene's materials were made twice) and GTAO's override material for each kind of mesh; the sky's light made in the same dry run (lit for real by `setMood` once its programs are made); the shadow maps' depth and distance materials on copies of the casters. Lights never come and go (the torch hangs from the scene, not the street the Ground scene hides): a light's count and shadows are compiled into every program. What the first frame does not need is compiled after it (`later`: the Ground scene's program, the slowest; `variants`: the lamps casting their shadows at night). The bloom's five blurs share one program (kernels padded with taps of no weight). A tour of the scenes and moods makes one more program (a lamp's shadow, at the first night).
* **Models** (`render3d/models/`, in metres, the tile's middle at the origin on the street's surface; the game's models are in tiles, so 1/4): `well.js` (the puteal turned from a profile with a moulded foot and lip, 36 S-shaped flutes and three rope grooves; two steps of seeded, bevelled, never-alike travertine blocks; the timber frame, iron shoes and straps, the pulley in its fork, the rope as tubes over the pulley, round the post and coiled on the step; the bronze bucket with its dent; the trough of clamped slabs; the lantern; `WELL` holds the measures, `wellLife()` swings the bucket and rope), `fountain.js` (the street fountain in four looks, below), `street.js` (displaced basalt paving ending in a row of edge stones, kerb, pavement, earth and 9,000 instanced grass blades, the house with its door, window, tiled roof and a torch) and `figure.js` (a 1.7 m mannequin). `shapes.js` has the helpers: `revolve()` (a profile turned, a hook to carve it, the seam's normals joined, vertex colour for grime and baked occlusion), `block()` (a rounded box pushed out of square by a seeded wobble, UVs projected in metres), `tube()`, `frameSweep()` (a profile run round a rectangle, mitred at the corners: a moulded basin, a pillar's cap), `merge()` (one mesh per material: the well is 13 meshes). Every model takes a level of detail (`lod` 0 to 2, below).
* **The street fountain** (`render3d/models/fountain.js`, F in the lab: `src/dev/labFountain.js`): a Roman street fountain (lacus) in four looks, poorest first, each fitting one 4 m tile with its spout at the back (-z): **1, a lava lacus** as most of Pompeii's forty-odd are (four thick slabs of the grey Vesuvian lava on a bottom slab, iron cramps leaded across the corner joints, a squat pillar with a spout block and a lead nozzle, the lead pipe up its back, a notch cut in the front slab for the overflow, a few lava flags); **2, a limestone lacus** on a step of limestone blocks, its pillar moulded at foot and cap with a carved head of a water god (beard and hair in locks) and a bronze nozzle in its mouth; **3, a marble basin** cut from one block, moulded at rim and foot, on a plinth, a fluted column with a bronze lion's head spout, in marble paving inside a travertine kerb; **4, a small nymphaeum**: a marble platform of two steps, a back wall stuccoed Pompeian red with an apsed niche lined in blue glass mosaic under a shell, two fluted columns carrying an entablature and a pediment, a nymph pouring from a hydria into a moulded basin, clipped box in terracotta pots. Each mesh is tagged with the state that shows it (`userData.when`: always; full, the water standing; flow, the stream, the rings and foam where it falls, the sheet over the notch and the wet stain in the street; dry, a puddle of green water on the floor and a pale lime stain; ice, icicles on the lip of a running fountain in a hard frost); `setFountainState` shows a state, `fountainLife(t)` runs the water (the stream's ripples scroll along it, the rings' outward: their own copies of the ripple texture, `streamMaterial`, `ringMaterial`; the rings, foam and stains fade at their edges by vertex alpha). Triangles at detail 0 / 1 / 2: 9.2k / 3.8k / 1.4k, 11.5k / 4.2k / 1.1k, 28.6k / 8.3k / 1.5k, 44.5k / 16.4k / 3.5k; the well 54.9k / 15.7k / 4.5k. The lab's Fountain scene puts the four on the well's street, running in front and dry behind, with labels and two figures, through the moods, seasons, snow and rain; Detail 0 / 1 / 2 (L) swaps in the simpler versions. `window.__lab` adds `fountains`, `setFountainLod(n)`, `fountainTriangles(lod)`.
* **The market, the forum and the warehouse** (`render3d/models/market.js`, `forum.js`, `warehouse.js`; their goods `wares.js`, shared building parts `masonry.js`; K, J, X in the lab: `src/dev/labCommerce.js`), each at its true size on its footprint (8, 8 and 12 m), designed from the excavated buildings, not the sprites. **The market** is a macellum after Pompeii's (a tholos over a water basin in its court), Puteoli's and Leptis Magna's (marble counters between the tholos's columns, a table of standard measures): eight Tuscan columns on a stepped octagon under a cone of tegulae and imbrices with antefixes and a bronze pine cone, a marble labrum of water, four marble fish counters between the columns; round the court eight stalls (a way in on each side), masonry counters painted with a dark socle and a red dado and topped with marble, under striped awnings on a timber frame that shade only the vendor (the counter top is open to the sky, so the game's camera sees it from the court and over the low wall behind); ## The look lab's models in the game (`render3d/modelPass.js`)

The WebGL back end draws the well (Puteus), the fountain (Lacus), the eight farms, the granary, the market, the forum, the warehouse, the prefecture, the engineer's post, the town walls with their gates and towers, the watchtower (Turris), the Navalia, the Statio and the Portus as the lab's models, in the look's materials, among the sprites. Classic does not change.

* **One scene, one light** (`render3d/sunRig.js`): the 3D ground's sun, sky (a PMREM of three's Sky), hemisphere fill and shadow map live in one scene with two slots, the ground's and the models'; three's sorting is off. With the 3D ground on, the models' opaque parts draw first (depth written; at High with the sun's shadow map, which they cast into, `renderModels(camera, 'opaque')`), then the ground's picture is copied in behind them (drawn into its own texture: see "The 3D ground"), then their water and other see-through parts (`'see-through'`); with the ground Off (or still loading) the models alone, in one draw. The light keeps its daylight key at every hour (the night's darkness is the 2D tint's, as for the ground), ACES and sRGB are set for that draw only. What rises out of the ground is clipped by the models' own shader (`uLookClipY` in the look's patch: nothing under y = 0), not by renderer clipping planes, which would have recompiled the ground's big shader.
* **Kits and instancing** (`kit.js`, `modelPass.js`): `models.js` says, per type, which look a building shows (`variant(b, place, ctx)`: a key, a state, a frost) and how to build it (`build(key, lod)`, metres). A look at a level of detail is built once (with three's colour management on for the while: the look's colours are sRGB to convert, the game's sprites plain bytes) into a kit, one part per material and state tag with each mesh's place baked in, and each part is one `InstancedMesh`: a frame refills the matrices of the buildings in view (`modelMatrix`: the footprint's middle, the building's turn plus the view's, a tile is 4 m whatever the footprint's size, so a 3 x 3 model spans 12 m, sunk while it rises), and a part shows only for the buildings whose state shows it (`partShows`: a dry fountain has no stream). A draw call a part whatever the number of buildings; a look unused for 600 frames is freed.
* **Looks of several kits** (`more`): a variant may return, besides its own kit, a list `more` of other kits each with the matrices (in the building's own metres) of its copies: a farm's farmhouse, its kind's things, its nine trees or six vine rows, its animals (their matrices refilled each frame: `farm.js moveAnimals`, `livestock.js herdPlaces`, each animal wandering a loop in its own cell of the pen and stopping to root or graze); a granary's goods by food. Each kit is instanced on its own across every building that shows it, so the farms in view cost a draw a part of each kit, not a draw a farm. Kits that are parts, not buildings, are built by their key's first word (`models.js MODEL_PARTS`, `modelFor`). A farm's list is kept per building (`farmModel` memo) and made again only when its look changes (a step is a fifth of a harvest; the season, its condition, its herd), never with the day's growth; a granary's when a place fills or empties.
* **Building kits** (`BUILD_MS`, `prefetch`): a frame builds kits at a new level of detail for 8 ms at most and draws what else it needs at another level already built (a look with no level built yet is built at once: there is nothing else to draw); with time left it builds the levels either side of the one in view, one kit a frame and only one it guesses will fit (from the level built: a finer level costs about four times a coarser one), and keeps them alive while their look is in view, so a zoom step mostly finds them ready. A kit is cheap to build: `shapes.js` keeps its rounded boxes as plain geometry (a RoundedBoxGeometry's `clone()` built the box again from its parameters, 0.2 ms a block) and `rural.js blk` keeps finished blocks by size (sizes to 4 cm, seven wobbles): the granary's building at full detail in 12 ms (62 before), a farmhouse in 7 (36). ## Trees and rocks (`render3d/flora/`)

The WebGL back end draws the map's trees and rocks as 3D models, with the 3D ground on (Ground High or Low; with the ground's sprites the 2D world stays 2D, its tree and rock sprites with it). Classic does not change.

* **Species** (`species.js`), designed from the vegetation of central and southern Italy and the western provinces as the botanists and the ancient writers (Theophrastus, Pliny's Natural History XII to XVI, Columella, Virgil's Georgics II) describe it, not from the sprites: the **Italian cypress** (a narrow flame, an accent among the others, never a wood of its own), the **stone pine** (a tall bare red-brown trunk under a flat parasol of needle tufts), the **holm oak** (a dense dark evergreen dome, grey beneath), the **downy oak** (a broad open crown of lobed leaves, russet in autumn, its dead leaves kept through the winter), the **sweet chestnut** (long toothed leaves, golden in autumn), the **oriental plane** (flaking pale bark, big hand-shaped leaves), the **white poplar** (a tall oval crown, silver beneath; not the columnar Lombardy poplar, a 17th century cultivar), the **white willow** pollarded for withies (Columella IV.30: a squat trunk, a knob, a mop of shoots, golden twigs in winter), the **wild olive**, the **bay laurel** and the **myrtle** of the maquis (white flowers in June and July), the **wild cherry** (white blossom in April, red in autumn), the **almond** (pink-white blossom on bare wood in February and March) and the **date palm** of the Desert Frontier's oases. Each has a size (a little under nature's, `FLORA_SCALE` 0.8: a tile is 4 m), a crown's envelope, a trunk, its limbs and twigs, its spray texture, its bark and its colours by look; the look by month (`lookOf`): leaf, spring (young leaves, lighter and fewer), blossom, autumn, bare, the downy oak's dead leaves, the myrtle's flowers.
* **Where** (`layout.js`, pure, tested in node): a tile's plants from its own byte of the variant layer, its place and its distance to water, never a neighbour's terrain, so clearing a tile never changes the trees round it. The habitat by the distance to water (`wet` 2 tiles or less: poplar, willow, plane; `fresh` to 6; `dry` beyond: pine, holm oak, wild olive), each climate's weights (`CLIMATES`: Tyrrhenian for Etruria, Liguria, Campania, Lucania and Bruttium; Adriatic for Picenum, Samnium and Apulia; Padane for Gallia Cisalpina, no pine or wild olive; Iberian for Hispania; Narbonese; the desert's palms) by the province's region (`data/sites.js`) and map type. Woods grow in stands: a smooth field over the map (`standField`: value noise whose lattice values are variant bytes of tiles 6 apart) picks a stand's species from the habitat's weights, about two trees in five are drawn from the whole mix, the accents (the cypress) only that way. A tile has a main tree near its middle, some a second smaller one, and on drier ground some a shrub. Rocks: an outcrop, boulders and scree by the tile's byte; on a volcanic province's map (Puteoli 50%, Volsinii 35%) lava boulders among them.
* **Trees** (`treeModel.js`): grown into the species' crown envelope (`ENVELOPES`: flame, parasol, dome, broad, tall dome, ovoid, mop, round, shrub), so the silhouette is the species' whatever the seed: the limbs head for points on the envelope round the trunk, their branches for points near those, the twigs nearer still (tapering tubes, `models/orchard.js limb`, the bark's texture tinted by the species). The foliage is cards, each a **spray** of leaves painted on the GPU (`surfacesFlora.js`, below) and cut out by its alpha: a third at the twigs' tips, the rest spread over the envelope by its area (a broad crown left with gaps, a dense one with darker sprays inside), each turned outward and up (the cypress's nearly upright, the stone pine's lying flat over its parasol), folded along its twig at the full level, drawn from both sides with the crown's outward normal (`materials.js LOOK_KIND.FOLIAGE`: the crown is lit as one mass), shaded darker toward the crown's middle and foot in its vertex colours, which carry the species' and the season's colour (the sprays are painted a pale neutral green: one texture for every season). Light through the leaves: a crown with the sun behind it glows at its rim. The date palm is its own: a ringed curving trunk, fronds as bent strips of the frond's texture, the dead ones hanging. Two shapes (seeds) a species; the tile's own scale and turn.
* **Rocks** (`rockModel.js`): limestone beds of jointed blocks, each stepped back from the one under it, boulders split from them, scree, dark lava boulders; stones from a superellipsoid (boxy for a bed's blocks, rounder for lava) cut flat by a few planes where they split, worn round, uneven by noise; sunk into the ground, darker toward the foot (contact shade), moss low on the side away from the sun and on ledges, the `crag` texture's lichens (grey-green crusts, orange Xanthoria, black streaks). Snow and rain as on every model.
* **Textures** (`surfacesFlora.js`, recipes as `surfaces.js`'s, painted on the GPU): sprays of ovate (holm oak, laurel, myrtle, cherry), lobed (oak), lance (willow, olive, almond), toothed (chestnut), palmate (plane) and deltoid (poplar) leaves, the stone pine's paired needles in a brush, the cypress's flat sprays of scale leaves, the palm's frond, blossom; each a 2 x 2 atlas of sprays (a branched twig, its leaves alternating along it, each leaf with its stalk, midrib, side veins and a low dome for the normal map, later leaves over earlier ones), the coverage into the albedo's alpha (`alpha: true`: the painter's third mode, `paint/recipe.js`); barks (pine plates, plane mottle, smooth with lenticels; the farms' furrowed `bark`); weathered limestone (`crag`). Painted with the models' at the start (`FloraPass` asks for them when it is made): asked for later they would hold the models back to their sprites while they paint.
* **Wind, snow, rain** (`materials.js`): the look's sway in the vertex shader (`LOOK_KIND.WOOD` and `FOLIAGE`: the whole tree slowly by its height, the wind's way in the world whatever the tree's own turn, gusts rolling across the map, each spray fluttering faster); snow settles on what faces up (the tops of crowns, branches, rocks) by the weather's cover; rain darkens bark and stone. No CPU work a frame.
* **The engine** (`flora.js`, the game's and the lab's): chunks of 16 x 16 tiles hold their tiles' plants and rocks; at each map revision the tiles whose flora comes or goes (`tileFlora`: forest with no road or building, rock with no building, as the 2D renderer draws their sprites) lay out their chunk again, so a building placed over a wood or a cleared tile shows at once. A **base** is a species in one shape (or a rock kind in one); each has a kit (`kit.js`) for its look this month at the level in view, built the first time it is wanted (a few ms), every part an InstancedMesh, a base's parts sharing one buffer of instance matrices: a draw call a part whatever the number of trees. Each frame the caller gives the chunks in view, the level, the month, the view's turn; the buffers are filled again only when one of those changed (a still view costs nothing), the trees nearest the camera first (the GPU's early depth test then throws away more of what is behind). A new look (a month, a level of detail) is built behind the old one within a budget a frame and swapped in whole once every base has it, as the sprites' looks are.
* **Levels of detail** (`floraLod`, by a tile's width on the screen, as the models'): from 300 device px the full trees (every twig, small folded sprays; at a pixel ratio of 2 the zooms 3x to 6x), from 180 the middle level (limbs and branches, sprays twice the size, a quarter as many, their colour texture only and no shadow taken: 1.5x and 2x), below it the **impostors** (`impostors.js`, 0.5x to 1x): the game's camera never changes its angle, so a picture of each tree taken from it stands for the model; baked on the GPU from the middle level into an atlas of 192 px cells (its colour before light, cut out, and its normal in the card's axes, so the sun and the sky still light it and snow settles by it), drawn as upright cards facing the camera across the ground (as the sprites stand: hidden and hiding by depth as they are), their height stretched by 1 / cos 30 to cover on the screen what the model does; every far tree of every species one instanced card, one draw call. Baked again when a season changes a look, behind the last season's pictures (an atlas of 48 cells holds both) and swapped in whole once all are baked, so a far wood never drops to its meshes for the frames the bakes take; never before the sprays are painted. Ground Low takes each level a zoom step sooner, as the models do.
* **In the game** (`floraPass.js`, `webglBackend.js`): with the flat ground nothing of it is prepared (its textures are asked for when the 3D ground is). Its group sits in the models' slot (`sunRig.js`), so it is drawn with the models' opaque parts (left out of their see-through draw), casts into the sun's shadow map (High; the middle and full levels, fewer than 3,500 in view; the trees just off the view's top and left, the sun's side, are kept to throw their shadows into it) and is left out of the ground's own picture. It draws only once its textures are painted, every base on the map has a kit and its programs are compiled (`compileAsync` on its group and a hidden card of every material of every kit built, shown or not, again when the shadows come or go; a new level or look is swapped in only once its programs are made, so the first zoom to 6x never compiles at its draw); until then the renderer draws the sprites (`drawsFlora`, `Renderer.render` leaves the tree and rock sprites out while it is true). Depth as the models': a walker behind a crown is hidden by it pixel by pixel, a building's sprite in front is drawn over it. Picking is by the tile, as before. The console's `flora` reports what is drawn, the level and memory; `flora off` draws the sprites, to compare.
* **Cost, measured** (RTX 5060 Ti, ANGLE D3D11, 1600 x 900 at a pixel ratio of 2, Ground High, the demo city, the camera over the map's biggest wood and panning, ms a frame with a 1 px read back, against v0.20.12 with the sprites): Large 0.5x / 1x / 2x / 6x 11.5 / 14.5 / 18.0 / 17.5 against 12.6 / 14.5 / 15.3 / 14.9; Uber 14.1 / 15.0 / 18.9 / 24.5 against 13.9 / 14.9 / 15.3 / 15.1 (2,850 / 1,230 / 730 / 440 trees and rocks drawn, 20 / 20 / 81 / 81 draw calls). The cost is the sprays' layers on the screen, not triangles: alpha to coverage, the sprays' normal and ORM reads and their shadow taps at the middle level, anisotropic filtering and twice the cards made a wood at 2x 40 ms and at 6x 48 before they went. Triangles a tree at the full / middle level (summer): cypress 4.5k / 1.8k, stone pine 4.3k / 1.0k, holm oak 3.4k / 0.7k, downy oak 3.3k / 0.7k, chestnut 3.7k / 0.8k, plane 3.3k / 0.7k, poplar 4.3k / 1.3k, willow 4.7k / 1.3k, wild olive 2.4k / 0.6k, laurel 2.6k / 0.6k, myrtle 1.9k / 0.7k, wild cherry 2.7k / 0.9k, almond 2.6k / 0.6k, date palm 1.5k / 0.3k; an impostor 2. Memory on the GPU: the sprays', barks' and limestone's textures about 40 MB with their mipmaps, the impostor atlas 18 MB, the kits' geometry 1.5 to 9 MB (the full level's built only when zoomed in).
* **The lab's Woods scene** (`src/dev/labWoods.js`, P): every species alone in both its shapes, labelled with its look this month; a wood on dry and fresh ground and its edge against a meadow; a river with its wooded banks; limestone and lava rocks; lone trees; drawn by the game's engine on the game's ground at the chosen month and level of detail (0, 1, 2 the impostors: L), through the moods, the seasons, snow and rain. `window.__lab.woods` has `setMonth`, `setLod`, `specimenAt`, `triangles(species, lod, look)`, `stats()`, `bytes()`; `__lab.surfaceImage(name)` shows a painted texture.

## The people (`render3d/people/`)

The WebGL back end draws the people of the buildings drawn as models moving, in instanced meshes skinned on the GPU (the look lab's People scene, `labPeople.js`, the minus key, shows every body, garment and clip). Every building with people in it draws them so: the temples, the oracle, the mission post, the school, the library, the academy, the forum, the senate house, the governor's house, villa and palace, the prefecture, the engineer's post, the barber, the physician, the baths, the hospital, the forts, the barracks, the military academy, the watchtower, the Navalia, the Statio, the Portus and the gardeners' yard. No kit merges a mannequin any more; `learning.js person` and `figure.js figureParts` are left for statues, which are carved and stand still. Classic does not change, nor does the sim: the people are render-only.

* **The rig** (`rig.js`): 25 bones of a man 1.70 m tall at rest (arms hanging a little out, palms to the thighs), metres, facing +z, his left at +x: root (the hips), spine, chest, neck, head; each side's clavicle, upper arm, forearm, hand, fingers and a prop bone at the hand's grip; thigh, shin, foot, toe. Every bone rests unrotated, so a pose is a rotation per bone about its joint and its skinning matrix is its world matrix times a translation by minus its joint (`pose.js write`). A woman is the same bones; a child is drawn at 0.78, what the head's bone carries scaled up 1.14 about the neck in the shader (`aActMisc.x`).
* **Poses and clips** (`pose.js`, `clips.js`): a clip is a loop of `dur` seconds whose pose is a function of its phase built from whole waves (`sin 2 pi k t`) and keyframes read round the loop (`track`, eased pose to pose), so its last frame runs into its first (the tests check every seam). A Pose takes the root's place and turn, FK rotations (Euler YXZ in the parent's frame: a hanging limb swings forward with a negative x rotation, the spine leans forward with a positive one, y turns left), targets for the hands and the feet solved by a two-bone solver (`ik2`: the elbow in the plane of a pole pointing back and out, the knee ahead), and prop bones placed outright (the pipes at the lips, the patera over the fire, the pump's beam) for the hands to reach. `stand()` underlies the standing clips: the weight shifted from leg to leg and held there (the hips over the planted foot, the free knee easing, the shoulders tilting against the hips), breathing, the head glancing about and holding. The walk plants its feet for real (`footAt`: heel strike, the sole flat, heel off, toe off, the contact point moving back at `WALK_SPEED`, then an arc forward), so on a route walked at that speed (scaled) the feet hold the ground. A toga wearer plays a clip's `@toga` variant where the clip leaves the left arm free (the folds on the bent forearm). The clips: idle, listen, talk, walk, carry, sit, write, read, orate, teach, pray (orans), sacrifice, flute (the tibiae), pump, hammer, sweep, count, give, recite, hold, shoulder, cheer, guard; and the work of the buildings converted after them: row and rowRight (at a rowing frame, the oar out on his left or right: catch, drive leaning back, the blade out and feathered, recovery), beat (the hortator's mallet on his block on the catch), drill (Vegetius's drill at the post: the shield up, a thrust of the gladius from behind it, a punch of the boss), march (a sentry's walk on his round, spear upright, shield on the arm), shoot (the composite bow: nock, draw to the jaw, hold, loose, the hand to the quiver and back), shave (the barber's razor down a cheek, a hand on the head) and shaved (his client, head tipped back), stir (a pestle round a mortar), dine (reclined on the left elbow on a couch, a cup in hand, reaching to the table, drinking), windlass (a crank turned, the body rocking into it), prune (spring shears along a hedge), reach (a roll taken from a cupboard's shelf, its tag read, put back), lie (abed on the back, the head on a pillow, breathing, turning the head, a hand to the brow now and then). A clip that works at something exports where that thing must be in the actor's frame (`PUMP`, `ROW`, `BEAT`, `WINDLASS`, `DINE`, `SHAVE`, `MORTAR`, `SHELF`), and the model puts its pump, thole pins, block, axle, couch, client, mortar or shelf there (the tests check the oar's line passes its thole, the mallet lands on the block, the hands stay on the crank). Baked once (`bakeClips`, 80 ms) into a float texture, a row a frame at each clip's own rate (3 to 40 a second: 4,006 rows of 75 texels, 4.6 MB, 115 ms; the tests hold it within 8,192 rows: the targets' GPUs read 16,384 and more, and the texture is only as tall as the clips baked), its table (start row, frames, rate) a uniform array.
* **Pieces** (`mesher.js`, `body.js`, `garments.js`, `hair.js`, `props.js`, `pieces.js`): everything a person is made of is a piece of its own, a skinned geometry (position, normal, uv in metres; `aBones` and `aWeights`: four bones, normalised; `aMat`: a material slot and a baked tone) built by its key at a level of detail: `body:<m|f|c>`; `tunic:<kind>:<short|knee|long>[:broad][:stola]`, `toga[:velato]`, `pallium`, `palla[:veil]`, `paenula`, `lorica`, `limus`, `caligae`, `helmet`, `bulla`, `wreath`; `hair:<crop|curls|bun|bald>`, `beard:<full|short>`; `prop:<name>:<L|R>` (patera, tibiae, tablet, stylus, rollOpen, roll, spear, scutum, broom, purse, axe, fasces, acerra, hammer, chisel, coin, beam, sack, oar, gladius, razor, pestle, cup, bow, arrow, crank, shears). A prop is skinned to its hand's prop bone, but a piece may name any bone: the bow's string has its nock on the other hand's prop bone, which the shoot clip puts at the drawing fingers (or on the string at rest), so the string is drawn back; a prop bone placed with `scale` near 0 hides what it carries (the arrow once loosed). Surfaces are grids of rings (`Mesher.grid`), each quad facing away from its vertices' `c` (the tube's axis) whichever way its rows run, normals averaged over vertices at one place (seams, split stripes). The head is one surface shaped and carved (`headPoint`: brow, sockets, the nose rising from a low bridge to its tip with its wings, philtrum, lips, chin, cheekbones, the jaw narrowing), its rows and columns crowded where the face is; eyes (sclera, iris, the lid's shade), ears, brows in the hair's colour. Garments are rings round the trunk's section pushed out (`drapeLoft`), folded by sums of waves deepening away from where the cloth is held (diagonal for a wrapped toga or palla), a fold's depth darkening its tone; the trunk's weights above the belt, the skirt's below (`skirtWeights`: the thighs' share growing downward, the middle shared so the cloth spans a stride, the shins below the knee for a long one, the back held by the root). Stripes (clavi) are split columns, so their edges stay sharp. The toga's folds over the bent left forearm are made in the toga's pose and brought back to rest through the inverse of their skinning (`fromPose`). Triangles, a citizen (body, tunic, hair) and a senator (with his toga): 5,660 / 1,377 / 343 and 7,282 / 1,809 / 451 at the three levels.
* **The material** (`material.js`): one MeshStandardMaterial on the wool's texture (`surfaces.js wool`), through the look's patch (`patchLook`: snow by the posed world normal on heads and shoulders, rain's wet, the clip under the ground), then the people's (`patchPeopleShader`; each line it swaps is checked, so a newer three or a changed patch throws, and the tests catch it): the skinning matrix at the top of `main()` (four bones in the two frames either side of the instance's time, blended; on a route two clips cross-faded at each change), applied to the rest position (a child's head scaled first) at `begin_vertex` and to the normal at `beginnormal_vertex`, then the route's turn and advance. A vertex's slot (`mesher.js SLOTS`) picks its colour (one of its instance's eight, packed 24-bit sRGB in `aActCol0` and `aActCol1`: tunic, mantle, skin, hair, trim, leather, accent, metal; or a fixed one: the eyes, wood, papyrus, gold, bronze, iron), with a tint (the lips', the nails'), its roughness and metalness, the woven texture's share (none on skin), its snow and its wet. One program for everyone; the shadow casters' (`peopleDepthMaterial`: depth for the sun, distance for a lamp) skinned alike, each mesh's `customDepthMaterial` and `customDistanceMaterial`. The time is the look's clock (`uLookTime`: with reduced motion everyone holds still).
* **Instancing** (`batch.js`): a piece at a level is one InstancedMesh across everyone who wears it, its instance attributes `aActClip` (clip, phase, speed, the route's pause clips), `aActRoute` (length, speed, pauses), the colours, `aActMisc` (head scale, the route's ends' facings). Each frame the model pass hands the batch the cast of every building it draws with the building's matrix; a signature of the set (each cast's id, the matrix, the seed) is kept, and the buffers are written only when it changes (a building into view or out, a state, the level, the view's turn): a still or panning view writes nothing. Each building gives its people a phase and a speed of their own from its place (`seedOf`), so two temples' priests never move in step. A piece is built the first time it is wanted within the model pass's 8 ms a frame (one build a frame may overrun: a full-detail body takes 10 to 20 ms; the same piece at another level stands in meanwhile, and a person with a piece neither built nor buildable waits whole for a later frame, never drawn half dressed) and freed after 900 frames unseen; the pieces are found by a number packed with the actor, not by a string. Their levels follow the size of a tile on the screen, their own (`peopleLodFor`: 300 device px and more the full body, 150 the middle): at a pixel ratio of 2, zoom 1 and under the far level (casting no shadow), 1.5 and 2 the middle, 3 and closer the full. A building not drawn draws nobody; the build ghost draws nobody. Warmed with the models (`warmPeople`: a hidden instanced proxy of the material in the slot; the depth caster's compiled apart under a render target, as the shadow pass draws it). A route's state has a twin on the CPU (`actors.js routePose`) the tests read: the turns take the short way, nothing jumps, the walk's clock runs on through the turns (and fades in across the loop's wrap); the walk plays at the route's speed over the clip's own stride (a laden man's is shorter).
* **The actors' API** (`actors.js`): a model's variant may return `actors`, a cast packed once (`cast(list)`, kept by state as `more` lists are): each actor `{ at, ry, body, scale, dress, hair, beard, props, clip, phase, speed, route, colours, seed, old, sync }` in the model's metres (the file's header says what each is). A route walks `length` metres ahead of the actor's facing and back at `speed`, pausing at each end in that end's clip, turned to face that end's way (`faceEnd`, `faceStart`, in the model's frame): the temple's priest walks from the foot of the steps, where he prays toward the god, to the altar, turns to it and pours. Colours come from the palette of Roman dyes (`DYES`: undyed wool in its sheep's shades, bleached white, madder, weld, saffron, woad, a green of woad over weld, walnut, ochre, the murex's purple) by the actor's seed when not given (`hash01`: no randomness, the same after a reload); a toga's border is its accent (its own white, a magistrate's purple), a tunic's clavi its trim (none unless given). Actors marked `sync` keep time together: the batch gives them the building's phase and speed alike (their own `phase` on top, 0 unless given), so a crew rows to its hortator's beat; every other actor gets a phase and a speed of its own.
* **Converting a building**: write its people as a function of its state returning actor specs in its own metres (`templeActors`, `schoolActors`, `forumActors`, `curiaActors`, `prefectureActors`, `tholusActors`, `sacellumActors`, and the rest below), drop its merged people from its kit, return `actors: cast(...)` from its variant (cached by state); a seated actor stands its feet `SEAT_H` under the seat's top; a prop a clip moves (the pump's beam) leaves the kit's copy tagged for the states in which nobody works it. The tests (`tests/people3d.test.mjs`) check every converted type keeps its people on its footprint at every view turn. **Adding a clip**: an entry in `CLIPS` (`dur`, `fps`, `pose(P, t, m)`, `toga` if a toga wearer plays it) of whole-cycle waves and `track` keys only (the seam test fails otherwise), feet given targets (`stand`, `sit`, `walkLegs`), hands by `P.hand` in the actor's or the chest's frame, props by `P.prop` or `propAlong`.

## The 3D ground (`render3d/ground/`)

The WebGL renderer draws the map's ground as lit 3D ground instead of its sprites: everything over it (buildings, trees, rocks, walls, bridges, walkers, units, effects) draws as before, on top, in the same order; the well and the fountain are 3D models in the same light (see "The look lab's models in the game"). Classic does not change.

**Every ground the game can show**, read from the code (the map's layers, what the 2D renderer derives, what the sim does to the ground), and how the 3D ground draws it:

* **The type map** (`groundMap.js`, pure: tested in node). One RGBA byte quad per map tile, uploaded as a texture the size of the map: R the kind of ground (`KIND`: the six terrains, plus kinds read from where a tile lies: grass at least 6 tiles from water dries to SCRUB in patches of about eight tiles, sand within 2.6 tiles of water is BEACH, a water tile's own ground is the BED its water lies on; SOIL is a layer the fields use, no tile's kind); G the road layer (links N E S W as `roadMask`, the surface: basalt for a street in town (a road with a building that is not a farm on any of its eight sides, so a block's corners and the crossings at its ends pave too, a road joining two or more such roads (a gap between blocks, a crossing where streets meet), or the Imperial road's fixed ends at the gates: Roman towns paved their streets), gravel for a country road, flagstones for a plaza, so a town paves itself as it grows along its roads; rubble; a bridge, which leaves the ground as water); B the signed distance from the tile's middle to the water's edge (+ land, - water, `128 + 16 d`, capped at 7.9 tiles: read between tile middles it gives a smooth coast round the tiles' corners, the water's depth from its edge out and the wet band on land); A the water's kind (a body 6 tiles deep somewhere is the open sea, else fresh water), whether a building stands there, whether the rubble is a fire's (its ruin's cause, `sim/ruins.js`) and whether it still burns (`game.fires`). No marsh: the map has none, and the ground must not suggest a kind of tile the sim does not have; the derived kinds are all looks of tiles the sim treats alike (scrub is grass, beach is sand). `GroundMap.update(hooks)` compares the layers it read last time (terrain, roads, rubble, the Imperial road, walls, aqueducts, and from its hooks farms, buildings, sites, their owners and burnt rubble), repacks the changed tiles and every tile within two of them (road and site links, and a street paved by a building on a diagonal or two tiles off), and reports the chunks it touched; the shore distance is worked out again only when water itself changed. What changes between the map's revisions (a field's growth, resting and idling; a fire going out) is repacked by `refresh(live)` on the tiles that can change (the farms' and the fires'), four times a second (once a second at Low, whose kept picture each change redraws), and uploaded only when a byte changed (growth in 64 steps: about one a game day a field).
* **The site map** (`groundMap.js` `detail`, filled from `groundSites.js`): a second byte quad per tile for what people made of the ground that is not a road. R the site (`SITE`: YARD, FOOTING, SOIL, GRAIN, VEG, FLAX, ORCHARD, OLIVE, VINES, PEN, PADDOCK), G a field's growth, B the sides that carry on into the same site (a field links only to its own farm's tiles, yards and footings to any: a town's trodden ground is one), resting, idle, the footprint's size, A the tile's place in its building and the building's turn (the shader finds where the farm's art stands its trees, vines and fence, and which way its rows run). `gameSiteHooks(game)` reads it from the game, never writing it: a farm's field by its crop and progress (its farmhouse's strip, the art's u 0..1 turned with the farm, is a yard), a horse ranch a paddock, a pig farm a pen, a native village's plots ploughed soil, any other building a yard (a garden or statue keeps its grass; a pier's rows over the water, the water), a wall, or an aqueduct where no road runs under it, a footing; it is worked out whole at each map revision (a building comes or goes) and the farms read again in between. With the 3D ground drawn, a farm's sprite draws only what stands up (`buildingArt.js FARM_BARE`: the farmhouse, its haystack, trees, vines, the pen's fence and pigs) and the ground draws its field; the Classic renderer is unchanged.
* **Chunks and turns** (`ground.js`): one quad per 32 x 32 tiles (`CHUNK`), all sharing one material and the type map: the ground is flat and all its detail is in the shader, so chunks only bound what is drawn (a 256 map is 64 quads). The quads lie in the MAP's coordinates in a group that `setTurn()` turns and moves into the view's (as `view.js toView`: a quarter turn is minus a quarter about three's y), so a view turn moves one matrix. Nothing is made or freed as the map changes: roads, plazas, rubble, yards and fields are bytes in the type and site maps (4 bytes a tile each: 256 KB each for the largest map, uploaded whole when anything in it changed).
* **The textures** (`groundSurfaces.js`, `groundTextures.js`): 20 procedural layers of 256 px (2x shows about 45 px a metre, so 256 px over 2 to 6 m is enough; WebGL's 4x shows about 90 and 6x about 136: grass, meadow and gravel at about 100 px a metre stay about one texel a pixel to 4x and soften a little at 6x, and basalt paving, flagstones and rocky ground, 43 to 64 px a metre, are magnified two to three times at 6x, where their shapes still read cleanly, with no repeat to be seen. Larger layers were not taken: the recipes' blurs and normals are in pixels, tuned at 256, so a bigger size changes the look, and four times the memory): pasture, meadow, scrub, forest floor, rocky ground, dune sand, beach, ploughed soil, river bed (the first nine in `KIND`'s order), gravel, basalt paving, flagstones, rubble, ripples, and for the sites a yard's trodden earth, a pen's mud, wheat, vegetables, flax and a fire's ash. Each packs colour with its height in the alpha, a normal map, and occlusion, roughness, how much of the pixel is living plants (the season tints only those) and in the ORM's alpha its seasonal marks: the pasture's daisies, the meadow's flowers and the scrub's blossom (shown by the season's `flowers`: a flush in spring, a few in summer, none in winter), the last leaves down on the forest floor (russet and gold by `leaves` in autumn), wheat's ears (they ripen first), a vegetable's ready colour, flax's flowers, the ash's embers. They are painted on the GPU, each into a layer of three array render targets, all in one go once their programs are compiled (see "How textures are made"): about 21 MB on the GPU with their mipmaps, nothing in the page. Recipes were tuned from screenshots on the GPU in the Ground types view: the forest floor is whole oak leaves in two layers, pine needles, twigs and moss; grass varies by sward and has bare earth only where worn through; scrub's cushions grow in clusters on bare stony ground.
* **The shader** (`groundMaterial.js`): three's MeshStandardMaterial (so the sun, its shadow map, the sky's light and the tone mapping light it as they light the well), its surface worked out per pixel. Kinds: the four tile middles round the pixel give four kinds and bilinear weights, read at a point bent by three octaves of noise (up to about half a tile), so the line between two kinds wanders; each kind's height is added to its weight, so where kinds meet the higher one's bumps win (grass tufts over the edge of sand, leaf litter under the trees creeping out), with a small bias by kind (`KIND_BIAS`: woods spread, sand gives way). Most pixels sample one kind. High samples each organic layer by hex tiling (after Mikkelsen's "Practical Real-Time Hex-Tiling": a triangle grid about half a repeat across, each corner the texture turned and moved its own way, blended by nearness and height), so no repeat lines up over a field (the earlier second copy mixed in by patches still showed a lattice down the screen at Zoom x2); never the furrows, a field's rows, paving or flagstones, which are square to the map. Large soft noise varies tone and dryness over a field. **Every sample a pixel takes is planned first** (slots: 0-3 the kinds, 4-5 its site, 6-8 its road's surface, kerb and margin, 9 rubble) and taken in one loop with a bound the compiler cannot see, the three hex taps written out inside: ANGLE inlines every call, and a sample written at each place that reads a layer took the compile from 0.8 s to 2.5 s (a loop over the taps' arrays cost another 1.8 s); planned, 1.3 s. Sites from the pixel's own tile, unbent: a clean straight edge where the site ends (a yard's softened by the grass's tufts leaning over it, a footing's worn and wandering), a field's headland raised a little; a field is ploughed soil with its crop over it as much as has grown (the rows' middles first, by the crop's height), young shoots yellow-green, wheat ripening to gold ears first, flax blue in flower then golden brown, stubble while it rests in winter, weeds coming in from the edges when it is idle; an orchard's and an olive grove's grass is hoed round each tree, a vineyard's along each row, where the sprite stands them; a pen is mud and straw inside its fence; a paddock and a footing are grass worn through in patches. Burned rubble is ash and charred beams with the grass round it scorched in a wandering edge, its embers glowing (breathing, in the emissive) while the tile still burns. Roads from the pixel's own tile: a distance field of a centre square and an arm to each linked side (corners rounded, junctions filleted), so roads bend and meet as the 2D art's do, 76% of a tile wide, with a worn verge (no wheel ruts: they read as streaks); a street's basalt has limestone kerbs and a gravel margin; a plaza is flagstones to its edges. Rubble is read between tile middles like the kinds, so a fallen block's rubble is one heap. Water from the shore distance: the bed seen through the shallows fading into the water's colour (a river green-blue, the sea blue), two scales of ripples drifting, a broken line of foam lapping at the edge, the sky's colour by Fresnel on the rippled normal in place of the environment's reflection (a hazy horizon made the water milky), glitter (High); a wet band on the land. Weather and season are uniforms that move smoothly, unlike the 2D art's steps: the season's position along the art's looks (`MONTH_LOOK`, day by day), snow by the weather's cover (`groundSnow`: by kind, little on roads which stay trodden grey, thin on yards, none on water; first on the bumps, then everywhere, keeping some of the ground's relief; a field's ridges and rubble's lumps break through deep snow, and a fire melts it round itself, leaving wet ground; the margins of water freeze under deep snow, never the middle, so a river still reads as water), wetness (`Weather.wet`, render only: it soaks in with rain and melting snow and dries over some nine game days) darkens what soaks it up and leaves puddles that mirror the sky in hollows, with rings while it rains (High). Textures are read with `textureGrad` and derivatives taken once at the top, as the kind loop branches per pixel. The value noises (some forty, by where they are read) are computed in three batches, what every pixel reads, what snow reads, what water reads, each one loop over a table whose bound the compiler cannot see, so the noise's code is in the program three times: ANGLE's D3D compiler unrolls a loop whose bound it knows, and the copies were half the shader's compile (1.2 s to 0.8 s alone on a desktop).
* **In the game** (`groundPass.js`, called by the WebGL back end): drawn each frame into a texture of its own (the shader tone maps and encodes sRGB itself, `GROUND_OWN_OUTPUT`), at `scale` of the WebGL canvas's pixels (the render scale's), and copied onto the canvas behind the models' opaque parts: the copy is a quad at the far plane with the depth test on, so it fills only what no model wrote; in the 3D world's scene (`sunRig.js`, shared with the models) with a sun (the 2D art's light: from the upper left of the screen at every turn) and the sky as image-based light (three's Sky in a PMREM, made once and again after a lost context). Drawn smaller, it is stretched smoothly; at full size it is copied pixel for pixel (against the old direct draw: the same picture but the map's outer edge, which loses its multisampling). The ground's shader is most of the GPU's work: on an RTX 5060 Ti at 2728 x 1800 (a pixel ratio of 2) while panning, 14 to 16 ms of a frame's 16 to 17 ms of GL work; at half the pixels each way the frame's GL work is 6 to 7 ms. The quads drawn after are not tone mapped: their raw shader writes the art's bytes whatever the renderer's output settings. **The night and an overcast sky stay 2D**: the renderer's light map multiplies the whole picture after the scene, ground and sprites alike, with its warm pools of lamplight; done in 3D as well it would darken the ground twice under sprites darkened once. So the 3D ground keeps its daylight key at every hour and in every weather: as the sun sinks (its height follows the time of day, so morning and evening light rakes across the ground's relief) or clouds come, a hemisphere light makes up exactly the light the sun no longer gives, and only the light's direction and softness change. **Depth**: the ground writes none, as its sprites wrote none: the sprite quads stand like cutouts on the ground line of their depth and some paint in front of it (a walker's feet, an overlay's flat footprints, which a ground writing depth hid in a first try), so the models clip themselves at the ground plane instead (`uLookClipY`): a building rising out of the ground still shows nothing under it. **Shadows**: the 2D building shadow shapes are drawn over the ground as before (`fill`); a building with a model casts its real shadow from the sun's shadow map (drawn with the models' opaque parts just before the ground; High only, fitted to the view, redrawn only while a model is in view, and cleared with the models left out of it wider than 96 tiles), and its 2D shape is left out. **Overlays, hints, the ghost, rings, signs** are drawn after the scene as always.
* **Quality** (*Settings > Ground*, `?ground=`, console `ground`): High (two samples a kind, puddles, glitter, model shadows, moving water) or Low (one sample a kind, still water, no shadow map). Low keeps its picture: its texture is drawn again only when the camera, the map or the light changed, and each frame copies it, so a still view costs a copy (good for a phone's battery too); it is drawn at most at 75% of the canvas's pixels each way (`LOW_SCALE`: panning redraws it every frame), and Low takes the models' simpler level of detail a zoom step sooner. Off is the flat sprites. Auto: Off on a software GL (no GPU), Low on a GPU in the processor (an Intel UHD laptop ran High at 100% of its GPU and sluggish) and on touch screens, High elsewhere; and an Auto ground at High goes to Low once when frames stay slow on the GPU at the render scale's lowest step.
* **Start-up**: the layers' programs and the ground's shader compile in the background side by side as soon as the back end starts (`compileAsync`, KHR_parallel_shader_compile); the shader, compiled at its first draw, froze a desktop for 2 s on ANGLE's D3D11, so it is compiled on a stand-in ground on the same arrays and under the very output state and lights it is drawn with (a compile under the quads' state gave another program and a 1.4 s freeze at the first draw). The layers are painted in one go when their programs are ready (about 12 ms of the page's time), at the first moment the game's own start leaves the page free (about 1.1 s after the pass starts on a desktop); the shader is ready at about 1.6 to 1.7 s (1.1 to 1.2 before the site map and hex tiling; the 3D ground first draws at 2.6 to 2.75 s from navigation instead of 2.1 to 2.2). The ground's sprites draw until both are (`stats.ground`: `loading`, then the quality; `stats.groundTexReady`). Measured, no long task at the first draw.
* **Cost, measured** (1600 x 900 at a pixel ratio of 1, the demo city in the middle of the map, a frame timed with the picture read back): on a GPU (RTX 5060 Ti, ANGLE on D3D11), the widest zoom: Large 12.2 ms at High, 13.0 at Low, 16.7 with the ground's sprites (351 draw calls against 193); Uber 10.9 / 10.4 / 15.2; the closest zoom about 10 ms in all. With every ground type (site map, hex tiling, 20 layers), the same city timed the same way before and after: Large widest 11.3 / 13.3 / 16.4 ms before, 11.5 / 11.2 / 16.1 after; closest 10.1 / 10.7 / 10.3 and 10.3 / 9.8 / 10.1; Uber widest 11.6 / 11.2 / 16.7 and 11.5 / 11.2 / 16.5, closest 10.5 / 9.3 / 10.0 and 10.3 / 9.7 / 9.8 (High / Low / sprites); at a pixel ratio of 2, High 34 to 36 ms both (the 2D canvas's copy is most of it): no change past the noise. ## Composition, render scale and the performance readout

* **The page's canvases** (`Renderer.mountLayers`, `useLayers`): with WebGL drawing, three canvases are stacked in `#app`: the WebGL canvas, a transparent 2D canvas over it (the overlay, `Renderer.over`), and #view on top. #view keeps the input exactly as before (events, cursor, `elementFromPoint` in `input.js`): it is made see-through (`opacity: 0`, which still takes clicks) and nothing is drawn on it, and the two under it have `pointer-events: none` (`.view-layer`). The renderer's `ctx` is the overlay's while WebGL draws and #view's otherwise, so the 2D passes after the scene need no change. While WebGL cannot draw (a lost context) Classic draws on #view, shown again, and the layers are hidden; `setBackend` removes the WebGL canvas when the player goes back to Classic. The overlay is cleared only when something was drawn on it, and hidden (left out of the page's compositing) on frames where nothing will be: the weather, no-road signs, the tool, the hovered tile, a selection, a fort being deployed, a dragged flag (`clearOverlay`).
* **What moved into WebGL** (`webglBackend.js post()`, `render3d/postPass.js`): everything between the scene and the weather, so the night darkens it as it always did and nothing of the scene is copied: particles, gulls and birds are painted by their own functions into cells of the live-art texture (`effects.js drawParticle`, `Renderer.fishingSpots`, `Ambient.drawFlock` and their boxes), drawn in front of everything (depth `FRONT`) after the build ghost; the cloud shade's puffs are quads of one soft disc painted once (`ambient.js cloudPuffSpec`, the same gradient cut to the same ellipse); the night's light map is a render target at half the view's pixels (less at a lower render scale), cleared to the sky's tint with the pools of light added (blend one, one: 'lighter'), then multiplied over the picture (destination colour times source: 'multiply' of an opaque picture), then the glows added; the lightning's flash is a colour added over everything (`Weather.flashAlpha`; the 2D overlay's drops are then not brightened by it, a difference no one sees in a flash a tenth of a second long). Against the copy at a pixel ratio of 2, the same scenes: day, an overlay, a selection and the build ghost differ only at the map's outer edge (0.3% of pixels); the night by up to 3 levels on 12.6% of pixels, dusk up to 7 (rounding in the light map).
* **Render scale** (*Settings > Render scale*, `?scale=`, console `scale`; `render3d/renderScale.js`): the WebGL canvas is drawn at `sceneScale` of the view's device pixels and the page stretches it to the view (`Renderer.sizeLayers` sets its CSS size; every quad is still placed in the view's device px, so picking and the overlay are untouched), its ground at `groundShare`. 100%, 75% and 50% are fixed; Auto (the default) steps along `LADDER`: the ground first (75%, 50% of the device pixels each way), then the scene (75%, then 50%), down to a quarter for the ground. It decides once a second from the frames as shown: a step down when the mean interval is over 21 ms, the page's own work is under three quarters of it (fewer pixels would not help a page busy with the sim) and, where the GPU timer has an answer, the GPU's time is at least half of it (a browser holding the page to 30 frames a second, a battery saver or a 30 Hz screen, with the GPU idle is not slow); frames slower than 120 ms are hiccups and left out, unless nearly all of a second's frames are, when the second is judged on them (a GPU that slow still steps down); a step up only after four fast seconds in a row (at most 17.6 ms, or the GPU busy under 35% of the interval: the rate is held down by something else), not within `wait` (6 s) of the last step down, and where the GPU timer says the next step's pixels fit in 11 ms; a step up followed within 4 s by a step down doubles `wait` (up to 2 minutes), so it never flickers between two steps; 1.5 s to settle after each. It starts at the top on a graphics card, with the ground at about one pixel per CSS pixel on a GPU in the processor (half the device's at a pixel ratio of 2), and at the scene's half with no GPU at all. The HUD, menus, text and the 2D overlay never change. Multisampling is asked for only on a graphics card (decided by a throwaway context before the real one): it smooths the models' edges, and on SwiftShader it was 2.3 times the frame at a pixel ratio of 2 (321 against 149 ms at the widest zoom).
* **The performance readout** (F3, *Settings > Show the performance readout*, console `perf`; `render/perf.js`): frames a second, the mean interval between frames and the slowest in the last second, the page's milliseconds by stage (sim, collect, draw, copy while there was one, overlay, ui; Classic draws as it collects, so its drawing is in `collect`), the GPU's own time for the WebGL frame from a timer query (`render3d/gpuTimer.js`, EXT_disjoint_timer_query_webgl2, a frame or two late; `n/a` where the browser has none), draw calls, the view's size and pixel ratio, the 3D scene's size and scale, the ground's quality, the models' state (`ModelPass.status()`), and the GPU the browser draws with (WEBGL_debug_renderer_info; with Classic, asked of a throwaway context). ## How textures are made (`render3d/paint/`)

Every procedural texture, the look's surfaces (`surfaces.js`) and the ground's layers (`ground/groundSurfaces.js`), is painted on the GPU, into the render targets the materials sample, as soon as its programs are compiled: a few milliseconds of GPU time for all 34. Nothing is painted on the CPU, kept in the browser or drawn as a stand-in: on a cold start the textures are in before the first frame. The CPU keeps only the models' own noise (`texgen.js`: where grass grows, how a block leans) and the paving's height, read back from the GPU.

* **A recipe** (`paint/recipe.js`) is data and a little GLSL, in stages: **fields** (the height and up to three more numbers per pixel, into a float target F: masks, a stone's id, the distance to its joint), a separable box **blur** of F's channels (a radius each: the neighbourhood's average the cavity reads, or a low-passed height), **colour** (the albedo in sRGB, mixed as a painter mixes, and occlusion, roughness and metalness, or for the ground plants, from F, its blur and noises of its own; and `dec` into the ORM's alpha, for the ground its seasonal marks) and a **normal** map by Sobel from a mix of F's and B's channels. A stage's noises are named specs (`fbm()`, `ridge()`, `cells()`: cells, octaves, a seed offset, gain, stretch, `uv`, `vu` or `diag` coordinates, a warp by an earlier noise) that its code reads by name, a `cells()` as a `Cell` (id, f1, edge, d). The single source of truth for a texture's look is its recipe.
* **The toolbox** (`paint/glsl.js`): the lattice hash in 32-bit integers (as JS's `Math.imul`, so a seed gives the same stone on every GPU), periodic gradient noise, fractal noise whose every octave tiles, ridged noise, Voronoi cells with the true distance to their borders, a downhill-safe `sstep`, the cavity, sRGB to linear. A stage's noises are not called one by one: they are a uniform table evaluated in one loop (`paintNoises`), so a program holds the noise's code once. ANGLE on Direct3D compiles every inlined call; written call by call a recipe compiled three times slower, and compiling is what painting costs.
* **The painter** (`paint/painter.js`, one per renderer): a texture is a set of uniforms (its recipe's index, its seed, a hash of its name, its noise table, its size), not a program. Programs hold four recipes each (`RECIPES_A_PROGRAM`; a uniform picks one) plus one for the passes they share (the blur, the ground's height range, the Sobel): ten for the 34 textures (nine for 28 before the ground's six site layers). Measured on ANGLE's D3D11, compiling the 28 side by side: 0.77 s as two programs, 0.43 s as eight, 0.75 s as 28. They are compiled with three's `compileAsync` (KHR_parallel_shader_compile, the page never waits on the compiler), and everything queued is then painted in one go: per texture the fields, the blur (two passes), for a ground layer its height's range (two reductions: the alpha is the height normalised over the layer), the albedo, the ORM and the normal, never binding a texture a pass draws into. Fields are float (`EXT_color_buffer_float`; half floats or bytes where a GPU has none), the outputs 8-bit as the materials read them, the albedo in an sRGB target (the hardware encodes, the mipmaps are made in linear light). A surface's targets are drawn once each and make their mipmaps then; an array target's mipmaps are made at its last layer, not at every layer. `painter.start()` begins compiling before the caller's task ends (the lab builds its models meanwhile).
* **The targets**: `surfaceTextures(name)` (`materials.js`) returns a surface's three 2D targets at once, at their final size (`surfaceTargets`), repeating every `metres`; `groundTextures(renderer)` (`ground/groundTextures.js`) the ground's three 20-layer array targets (`arrayTargets`), about 21 MB on the GPU with mipmaps and nothing in the page. Their pixels are undefined until painted: the lab's first frame waits for `surfacesReady()` and the ground's `ready`, the game draws the ground's sprites until then.
* **Read back**: the street's paving is a mesh displaced by the basalt's low-passed height (its blur's y), read back once with three's `readRenderTargetPixelsAsync` (a pixel buffer and a fence: the page does not wait for the GPU); the paving lies level until it comes, a frame or two later. `painter.readPixels(target, layer)` reads a target's bytes at once, for checks only (`__lab.textureReport()`, `src/dev/texReport.js`).
* **A lost context**: the painter listens to the canvas, compiles again and paints every texture again once it is restored; a target its owner freed (`painter.forget`) is left alone.
* **Measured** (RTX 5060 Ti, ANGLE on D3D11, headless Chromium at 1600 x 900, a fresh profile each time; the sandboxed iframe is `<iframe sandbox="allow-scripts">` over http, as the artifact viewer, where IndexedDB was blocked and every visit painted again; ms from navigation):

## Audio (`audio/`)

* **Sound effects** (`sfx.js`): a few oscillators or a noise burst per sound. The app suspends the audio context while the tab is hidden.
* **Starting the sound**: browsers hold audio back until a user gesture. `App.tryAutoplay()` creates the context at boot (and when a background tab becomes visible) if the music would be heard; where autoplay is allowed it simply runs. Otherwise the main menu shows the **title gate** (`ui.js` `showAudioGate`, `menus.js` `titleGate`): its click, tap or key press starts the menu music, and a short guard afterwards swallows the rest of that gesture (a double-click's second click, a held key's repeats) so no menu button is pressed by it. Unlock listens to `pointerdown`, `pointerup`, `touchend`, `click` and `keydown` (a touch only counts on its release); the context's `statechange` drops the gate whichever way the sound started.
* **Music** is generated, never recorded, in three layers:
  * `composer.js` writes the notes and nothing else (pure, deterministic for a random source, tested in node). A `Piece` has a mood (tempo range, meters, modes, keys, lead instrument, drum and lyre styles, the silence after it, a target length), an opening (`INTRO_STYLES`: who starts), and a form built to the target (a few minutes): the opening, then rounds of 4-bar sections repeated until it is long enough (A the theme, A2 moved up or down, B a higher answer, C a calmer contrast on the other pipe with a thinner accompaniment, an interlude for the lyre alone, A3/A4 ornamented), then an ending (battle music has none). A one-bar theme returns varied in the A sections; harmonies are perfect fifths under a drone; melodies move mostly by step, put chord tones on strong beats and long notes, and end phrases on the tonic or the fifth. `Piece.texture()` decides which parts play in each bar. `TRACKS` is the library for menu, day and night: ten named pieces, each written from a fixed seed (`seededRandom`) with its own key, tempo, meter, pipes, opening and length, so a track sounds the same every time; `pickTrack` chooses at random, never one of the last `TRACK_MEMORY`. `windDown()` ends a piece early at the end of its phrase. `nextBar()` returns timed events (`{ t, dur, inst, midi, vel, pan }`).
  * `instruments.js` synthesizes them: Karplus-Strong lyre (cached per note, tuned with `playbackRate`), reed pipe, pan flute, drone, frame drum, horn, sistrum, plus a generated reverb and a gentle high-pass. `Studio` holds what all pieces share; each piece plays through its own `Band` so it can fade out while the next begins.
  * `music.js` schedules bars half a second ahead on the audio clock (look-ahead scheduling: steady timing even when frames stutter). `nextPiece()` plays a track for moods that have them, a new piece otherwise. Raiders and festivals take over at once (the old piece fades out); between calm moods a track that also belongs to the new mood plays on, and one that does not winds down to its ending. It leaves silence between calm pieces, plays a track by name (`play`, console and music lab), and can render any mood offline (`renderMood`) for WAV export and tests.
* The app picks the mood every frame (`App.musicMood()`): raiders or Caesar's legions on the map (the same danger music), then a recent festival (`festivalDay`: within 24 days (`FESTIVAL_MUSIC_DAYS`) of the last one held this session, so a festival every 2 months still leaves days of ordinary music), then night (the sky's lamps) or day; the main menu has its own. Victory plays festival music, defeat the night music.
* Checking what you cannot hear: `tests/e2e/music.html` plays each track and each mood, and renders every mood and measures peak and loudness and each instrument's tuning; the smoke test runs `App.musicSelfCheck()` in the built game.

## Adding things

* **Turning a new building**: it turns by itself if its art keeps to `draw.js` (boxes, roofs, polygons through `P()`, windows, doors): check it at every turn in `tests/e2e/artsheet.html?turns=<its key>`.
